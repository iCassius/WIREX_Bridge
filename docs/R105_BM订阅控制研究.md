# R105 BrandMeister 组呼订阅与控制研究

查阅日期：2026-10-27。范围限于 BM 官方 API 文档、BrandMeister 官方帮助页、MMDVMHost/DMRGateway 源码及设备厂商 Homebrew/MMDVM 手册。未登录 BM、未读取本机密码或 API key、未调用 BM API、未发送 UDP/DMR 语音或控制包。本轮只新增独立请求规划模块和 mock 验收脚本，没有修改启动器、UI、profile 或 Native 媒体会话。

## 结论

1. BM 官方 API Manager 文档描述了静态 TG 的添加/删除和清理动作。`pistar-bmapi` 第三方客户端源码展示了对应写入/动作路径和字段；BM 官方 OpenAPI/schema 未找到。设备 profile 的 `GET /v2/device/{id}/profile` 及其字段只在第三方 gist 中观察到，本轮没有在官方 Pi-Star Dashboard 或 WPSD 源码中找到同一读侧实现。适配器把这些读侧内容当成待验证假设；只有合成 fixture 的解析结果，不足以启用静态订阅自动调和或称为 BM 读回确认。
2. BM 官方把动态 TG 描述成经 repeater/hotspot 由用户 PTT 激活。未发现 BM REST API 提供动态 TG 的“订阅/加入”写入端点。SharkRF 的 Homebrew/MMDVM Quick Call 手册说明，设备可以发送短促的空组呼叫来连接动态 TG；空呼叫不含语音，但仍是一通 DMR 组呼，且会显示在 BM Dashboard。软件要走动态路线，应把这个动作作为显式用户操作，不得把它伪装成仅本地收听开关。
3. BM 官方说 USA Master 的动态 TG 超时为 15 分钟；非 USA Master 由各 Master 决定。BrandMeister USA 文档另列出 5 分钟 Hold Off。不能把这些数值直接写死为 BM China 4602 的当前行为。
4. BM API 的静态订阅可以在设备上配置多个 TG。它们是 BM 服务器向节点转发来话的配置；软件仍需要维护独立的本地 RX 允许集合和来源排除集合。BM 官方 USA 文档提示同一时隙上静态组过多时，繁忙组可能占用该时隙。即使 UI 选择其他 TG，本地过滤也不会让 BM Master 自动切换到该 TG。
5. BM API 管理用的 `slot` 与 DMRD 语音帧中的 TS1/TS2 是两个不同字段。Pi-Star 为 simplex hotspot 使用 API `slot=0`，为 duplex repeater/hotspot 使用 `1` 或 `2`；simplex 的实际 DMR 媒体仍可处于 TS2。WIREX 的 BM 设备类型和 API 资源 ID 应以 BM Dashboard 中注册设备为准，再单独配置网络管理 slot 与 DMR 媒体 slot。

## 组呼、单呼与本地收听集合

动态/静态 TG 都是组呼路由概念。BM 设备订阅 API 修改的是设备上的静态 TG 集合；动态 TG 由一次组呼激活。它们不会替代 WIREX 自己的来话目的过滤、来源身份排除、RX/TX 仲裁或当前来话 UI 状态。

单呼使用 DMR Private Call（FLCO `USER_USER`）的目标 Radio ID，不属于静态 TG 订阅。R105 查到的 BM v2 订阅端点只管理 talkgroup 项；当前 QSO 可通过 `dropCallRoute` 动作结束，但没有找到“静态订阅某个个人 Radio ID”或“静默监听某个单呼 ID”的官方 API。单呼应沿用 Native 的私呼目标/回音规则和 BM 网络通话状态，不应套用 TG 静态订阅语义。

建议将状态拆成这些独立集合/值：

- `bm_static_subscriptions`: 经 API 读回的 `(device_id, api_slot, talkgroup)` 项。
- `bm_dynamic_subscriptions`: API profile 中读回的动态 TG 项；若 profile/schema 未知，报告 `unknown`，不能根据一次 quick call 即显示“已连接”。
- `local_rx_allowlist`: 本地允许进入语音接收管线的 `(destination_id, dmr_slot, call_kind)` 集合，可选单组或多组。
- `blocked_sources`: 按来话 Source ID 做本地排除；排除某来源不删除 BM 静态订阅，也不触发 `dropDynamicGroups`。
- `tx_target`: 独立的单一发射目的与组呼/私呼类型。

本地过滤只会挡住本机播放/显示，不会改变 BM Master 当前向这个 DMR 节点推送的组别。BM USA 的静态组说明建议不要在同一 slot 设置太多静态组，因为繁忙组可能占满该 slot；当前 4602 Master 在多静态组活跃时如何仲裁、WIREX 端是否会连续收到多个流，须通过该 Master 的设备状态和受控实测确认。不要把“本机过滤掉当前流”描述成“BM 自动切换到下一组”。

## 动态 TG、Quick Call、TG4000 与驻留时长

### 动态 TG 激活

BrandMeister 官方 [Dynamic vs Static](https://help.brandmeister.network/talk-groups/dynamic-vs-static/) 文档把动态 TG 描述为用户经 repeater 或 hotspot 短时 PTT 激活；官方文档没有给出纯 REST 动态订阅写入端点。官方 [API Manager](https://help.brandmeister.network/hotspots/api-manager/) 文档列出的 API 管理操作是静态 TG 增删、Drop QSO 和 Drop All Dynamic。

[SharkRF openSPOT3 手册](https://manuals.sharkrf.com/openspot3/en/side-panels-tools-page.html#quick-call) 描述 Homebrew/MMDVM Quick Call：发起一个短暂、无语音内容的组呼，作用类似短按 PTT（kerchunk），用来动态连接指定 TG；手册也说明这种空呼叫会出现在 BrandMeister Dashboard。它证实了“无需承载人声的短组呼”是现有 Homebrew/MMDVM 设备采用的动态连接方式，但没有规定 BM 各 Master 的最低帧数、重复间隔或所有 Master 的接受规则。

因此，若 WIREX 后续支持动态 TG 快捷操作，应把它实现成独立 `quick_call_group(tg, dmr_slot)` 行为：只由用户明确触发；生成协议有效的短空组呼；在 UI/日志里报告“已发送 quick call”，随后等待 API/profile 或网络来话提供确认。不得将 HTTP `GET /action/dropDynamicGroups/...` 当成订阅或读操作。连续发送同一 quick call 可能重置 Master 的动态驻留计时并在 Dashboard 产生多条呼叫事件，不能由后台轮询自动触发。

### TG4000 清理

openSPOT3 Homebrew/MMDVM 手册说明：短暂 Group Call 到 TG4000 会断开动态 TG 和 reflector；Private Call 4000 用于解除 reflector。BrandMeister API Manager 将 `Drop All Dynamic` 和 `Drop QSO` 分成两个动作。因此：

- Group Call TG4000 是网络组呼控制动作，不能删除静态 TG。
- REST `dropDynamicGroups/{slot}` 清除该 BM 设备 slot 上的动态 TG；`dropCallRoute/{slot}` 结束当前 QSO。它们不能代替本地静音或源 ID 排除。
- simplex 热点在 BM 文档中有 auto-static 行为。第一次激活的组可能作为 auto-static 保留，下一次激活将新的组设为 auto-static；具体转为动态或被清除的细节以 Master 行为为准。对 simplex 节点而言，切换前用 TG4000 清理再 quick call 新组是设备手册展示的常见动作，但本机 WIREX 的设备分类尚未由 4602 服务器资料确认。
- duplex 节点清理动作必须选择实际使用的 DMR 时隙。API 的 slot 0 设备标记不应直接变成 DMRD TS0。

### 驻留与服务器差异

BM 官方动态/静态帮助页称 USA Master 动态 TG 的超时为 15 分钟，并明确其他 Master 的时间取决于各自配置。BrandMeister USA 文档当前也标出 USA Master `Hold Off=5 Minutes`。这些是服务器流量路由参数，不等同于本地 `CallHang`、Native RX timeout 或 PTT 操作超时。

对 BM China 4602，R105 公开文档检索没有找到能确认动态驻留时长、Hold Off、auto-static 与多个活跃 static TG 仲裁方式的官方页面。实现必须将这些参数视为服务器待确认状态，不能预置“15 分钟”后声称这是 4602 的实际结果。应在用户授权的后续设备联测中记录调用前后的 profile、实际流量 Source/Destination/TS、每次 quick call 时间和 BM last-heard 事件，再单独估计该 Master 的计时行为。

## BM API v2 请求面与认证

下表中的写入与动作 URL/JSON 是 Pi-Star `pistar-bmapi` 对 BM v2 的第三方客户端实现观察，不是 BM 官方 OpenAPI 规格。profile 读侧 URL 和字段只在第三方 gist 中看到，本轮未从官方 Pi-Star Dashboard 或 WPSD 源码确认。此轮实现仅创建请求计划和 fake transport 结果状态；没有 live HTTP transport。读侧假设须先有可信 fixture，再经明确授权的只读 live 核验，不能据此自动确认静态订阅。

| 行为 | 请求 | 请求体 / 读回 | 证据和边界 |
|---|---|---|---|
| 读设备 profile（待验证） | 第三方 gist 使用 `GET https://api.brandmeister.network/v2/device/{deviceId}/profile` | gist 中 jq 代码读取 `staticSubscriptions[]`、`dynamicSubscriptions[]`，项内读取 `talkgroup` 与 `slot` | 这是第三方脚本片段，不是 Pi-Star/WPSD 官方实现或 BM 官方 schema。只有字段与响应经可信 fixture / 后续授权只读核验后，才能把 live 读回标为已知。 |
| 添加静态组 | `POST /v2/device/{deviceId}/talkgroup` | `{"slot":0,"group":91}` | Pi-Star 工具将 `group` 和 `slot` 作为 JSON 字段。simplex hotspot 用 API slot 0；duplex 使用 1 或 2。 |
| 删除静态组 | `DELETE /v2/device/{deviceId}/talkgroup/{slot}/{group}` | 无 | Pi-Star 工具实现。删除目标应精确匹配设备、API slot 和 TG。 |
| 清除动态组 | `GET /v2/device/{deviceId}/action/dropDynamicGroups/{slot}` | 无 | URL 形式、方法由 Pi-Star 工具实现；虽是 HTTP GET，却执行删除动作。按用户明确操作调用。 |
| 结束当前 QSO | `GET /v2/device/{deviceId}/action/dropCallRoute/{slot}` | 无 | URL 形式、方法由 Pi-Star 工具实现；这是控制动作，不是查询。 |
| 读静态/动态 profile 后核对 | 再执行 profile GET | 解析成功才把服务端状态置为已确认 | 不要以 POST/DELETE 2xx 单独证明服务器实际状态；202、空响应、超时或未知字段都不能伪装成成功。 |

BM 官方 [User API keys](https://news.brandmeister.network/introducing-user-api-keys/) 说明 API key 是账户级数字密钥；2022-08-19 之后新建的 key 属于 v2，格式为 JWT。官方也明确 API key 与 SelfCare 登录密码无关，撤销 key 会禁用使用该 key 的应用。Pi-Star 客户端把它放在 HTTP `Authorization: Bearer <API_KEY>` 头中。

它与 [Hotspot Security](https://help.brandmeister.network/dashboard/hotspot-security/) 密码属于不同接口和用途：hotspot security password 用于 DMR Homebrew 网络设备认证；API key 用于 HTTPS BM 账户/设备管理。两种秘密必须分开存储、单独输入、单独清除；绝不互相回退，不写进同一配置字段，不出现在命令行、诊断日志、JSONL 状态或包 manifest。开发和验收只用合成 Bearer 值，不读取或引用现有本机凭据。

BM API 操作需要指向仪表板中属于该账户的精确 device ID。Pi-Star 从本机 MMDVMHost/DMRGateway 配置中读取当前 DMR ID，并对 SIMPLEX hotspot 使用 API slot 0；实际本机 API 目标 ID、ESSID/SSID 规则和 4602 Master 识别的设备类型本轮未访问，也不应根据当前 DMRD `TS2` 过滤器猜测。应用配置中分别保留 `bm_device_id`、`bm_api_slot` 和媒体 `dmr_slot`。

## MMDVMHost 与 DMRGateway 源码观察

- [MMDVMHost `DMRSlot.cpp`](https://github.com/g4klx/MMDVM-Host/blob/master/DMRSlot.cpp#L2559-L2724)：RF Group Voice Header 解码出源/目的和呼叫类型，先通过 Source ID、TG/slot 校验，再进入 `AUDIO` 状态，并将 LC header 经 `writeNetworkRF` 转发。正常结束由 `DT_TERMINATOR_WITH_LC` 生成 EOT。代码没有独立的 BM HTTP “join TG”调用，也没有在 `DMRSlot.cpp` 里特殊实现 TG4000；服务器侧 TG 路由动作在 DMR 组呼/网络协议层。
- [MMDVMHost `DMRNetwork.cpp`](https://github.com/g4klx/MMDVM-Host/blob/master/DMRNetwork.cpp)：Homebrew 网络模块处理 DMRD 媒体封装。MMDVMHost 所证明的是正常 DMR 数据流，不是 4602 Master 对一个无语音快速组呼的具体接受结果。
- [DMRGateway `DMRGateway.cpp`](https://github.com/g4klx/DMRGateway/blob/master/DMRGateway.cpp#L3172-L3222)：Gateway 对收到的组呼帧应用 `RewriteTG`/pass-all 规则，再把匹配的 `CDMRData` 写入选定 DMR network，并按射频 slot 启动本地网络切换 timeout。它负责路由与改写，不调用 BM REST API，也不提供 BM 动态订阅管理。
- [DMRGateway 配置示例](https://github.com/g4klx/DMRGateway/blob/master/DMRGateway.ini)：`TGDynRewrite` 和 `PCRewrite` 是 Gateway 的本地号码改写/反射器兼容规则。配置示例中的 4000/4001~5000 映射不等同于 BM API `dropDynamicGroups`，也不能证明给 BM 服务器加静态订阅。

以上 upstream 仓库的 `master` 分支会变化；引用的是 2026-10-27 访问时的页面内容。后续实现应在交付证据中固定实际核对的 commit/hash 和行号。

## 独立离线适配器设计

本轮新增 `tools/bm-subscription-api.psm1`（Windows PowerShell 5.1）和 `tools/test-bm-subscription-api.ps1`。模块生成 HTTPS 请求计划、从显式 token file 读取 Bearer token、再调用必填的注入式 transport；它没有内置真实 HTTP transport，因此默认不能访问 BM。返回值只保留 HTTP 状态码和已清理过 token 的 body，不把 transport 响应对象原样传给调用者。mock 只使用合成 token。测试命令 `powershell.exe -NoLogo -NoProfile -File .\tools\test-bm-subscription-api.ps1` 已在 Windows PowerShell 5.1 通过。模块没有接 UI/启动器/profile 或 Native 媒体会话。

若后续增加 live transport，应仍通过独立、显式提供的 transport 注入，禁止默认请求 BM。每台设备的 API key 应从独立 token file/Credential Manager abstraction 读取；token 不应通过命令行传入。当前模块只接受固定 `api.brandmeister.network` host 的请求计划，并在 transport 返回后把 request object 中的 Authorization 值替换为 `[REDACTED]`。

请求计划最小输入：`deviceId`、`apiSlot`、`desiredStaticGroups`、当前读回 profile（可 Unknown）、动作类型。输出只描述将要发出的 HTTPS method/path/body/header来源和安全类别；不得持有或打印实际 token。`ReadProfile` 可以不传 slot，因为它读取整台 device profile；静态修改、清理动态 TG 和结束当前 QSO 则必须显式指定 API slot。profile parser 使用 `Invoke-BmApiRequestPlan` 的 read invocation 元数据，保存设备 ID、读请求 ID、HTTP 状态码、开始/完成时间及其对应 mutation 请求 ID；静态变更读回要求 GET 请求开始时间晚于 mutation 完成时间，只有“较晚完成”还不够。mutation invocation 也必须匹配相同设备和动作。调用者不能另传任意“读回时间”来绕过时间顺序核对。建议操作流：

1. 用户提供静态订阅目标集时，先读取 profile；仅在返回结构已按已知 schema 成功解析后计算差集。
2. 当前集合缺目标时创建单项 POST；当前集合多余时对确切 `(slot, talkgroup)` 发 DELETE。每台设备串行调度，先后请求不并行。
3. 不重复 POST 已存在项；不重复 DELETE 已不存在项。对超时、连接断开、202 或非明确成功码，读回 profile；只有解析后确实符合期望集合才报确认，否则保留 `unknown/pending/error`，不得盲目重放。
4. 这些“幂等”保证来自本地差集调和与回读，不来自 BM 服务器承诺 POST 本身幂等。API profile 可能由用户在 BM Dashboard 或另一热点管理器并发修改；每次新操作都重新读取，避免把未知远端变化覆盖。删除/添加的确认对象同时核对计划 ID、BM device ID、mutation invocation 的 device/action、读回计划关联的 mutation ID，以及 GET 开始时间确实晚于 mutation invocation 完成时间；旧 snapshot、并发中已经开始的 GET、跨 device 或跨 plan 的读回会返回 `unknown`。401/403 等写入拒绝会让 mutation 结果保持未确认，即便单独观察到的 profile 已符合目标，也只报告读到的状态，不将其归因为这次写入成功。
5. `dropDynamicGroups` 和 `dropCallRoute` 归为有副作用的 action request，要求显式调用；不要挂到刷新按钮或状态轮询。因为 `GET` 方法不等于读操作，未来 live transport 必须禁用缓存并限制 redirect，不能让带 Bearer token 的请求转发到非官方 host。当前没有 live transport，也没有设置连接/响应 timeout；未来加真实 HTTP 实现时应限制连接时间和响应等待时间。动作返回后只刷新 profile/通话状态，不以“HTTP 200”推断所有动态组/通话均已清除。
6. Quick Call 不进入 HTTP adapter。由媒体/DMRD 单独实现和调度；API 与数据面用同一明确 device ID，但分别报告请求已送、服务端 profile 读回、实际 RX 首帧三个阶段。

凭据提供器从一个单独 token file/Credential Manager abstraction 取得 API token；路径不硬编码到 profile。本轮 mock 只使用 `TEST-ONLY-BEARER-DO-NOT-USE` 这类合成值。HTTP 日志只显示 `Authorization: Bearer [REDACTED]`。设备 Hotspot Security password 继续由当前网络会话管理，不允许 planner 请求它。

## Mock 验收建议

所有请求走 fake handler；用合成设备 ID、TG、slot 和 token。验收不打开网络、不访问 BM 域名、不发送 UDP/语音或 RF：

1. Bearer API token 只在 HTTP Authorization header 中；不得进入 URL/body/log/异常文本/PowerShell 命令参数。Hotspot Security password fixture 不得被请求计划读取。
2. 正确构造 POST、DELETE、profile GET、dropDynamicGroups 和 dropCallRoute；确保 0/1/2 的 API slot 不会被误写成 DMRD TS0/TS1/TS2 字段。
3. profile 有多个 static/dynamic 项时正确解析；slot 缺失、类型错误、额外字段、无效 JSON、未知数组名都保留 Unknown，并禁止写入目标集合。
4. Desired state 与当前状态一致时 planner 不产生变更；差集有两个项时分别计划精确 POST/DELETE；不同 DMR device 或 slot 不交叉删除。
5. POST/DELETE 成功后 profile readback 符合目标才确认；profile 仍旧、返回 202、超时、401、403、404、409、429、500、错误 JSON 均输出准确状态且不出现虚假订阅确认。
6. 变更请求超时后 fake server 模拟“远端已应用但响应丢失”和“远端未应用”两种情形，planner 都先读回，再仅根据状态呈现或规划下一步。
7. 即使 `GET .../action/dropDynamicGroups/...` 返回成功，也断言它是 action（执行调用计数增加），不会被普通 profile refresh 调用；重复点击不得由定时 poll 自动重试。对 `dropCallRoute` 同样检查。
8. Quick Call 计划不得出现在 API request plan；它必须被标成单独的数据面命令和显式用户触发，并在文档/UI 状态中区分“空组呼已发”与“BM 动态订阅已确认”。

这组 mock 只能证明本地请求计划、认证隔离、响应 token 清理、HTTP 状态映射及带设备和请求时间关联的状态机处理固定响应正确；它不能证明 BM 服务器接受 API 写入、4602 的时隙/静态组仲裁、动态驻留时间、Quick Call 触发效果、真实下行音频或 RX/TX 同时切换行为。

## 未确认项与下一步证据

- BrandMeister 未公开发现 v2 REST API 的完整官方 OpenAPI。静态增删和 action 路径来自第三方 `pistar-bmapi` 客户端；profile GET 路径/字段来自第三方 gist。检索官方 [Pi-Star Dashboard 源码](https://github.com/AndyTaylorTweet/Pi-Star_DV_Dash) 与 [WPSD 项目代码入口](https://w0chp.radio/articles/how-to-contribute-to-wpsd/) 时，没有找到能确认该 profile 读侧 URL/schema 的官方代码证据。因此 profile 读侧仍是实现假设；需要固定 fixture 和后续获授权的只读服务器核验。合成 fixture 通过只能验 parser/request state machine，不能启用 live 静态组自动调和或标记 BM 状态 confirmed。
- 4602 Master 的 dynamic timeout、Hold Off、auto-static、同 slot 多静态 TG 活跃仲裁、simplex/duplex 识别与Quick Call 最短有效帧数均未知。
- BM API slot 0 是否适用于本机注册的 DMR node/ESSID，须从只读 dashboard/device profile 确认；不可从 R104 的 DMRD TS2 直接推导。
- API 调用成功能否及时反映到 BM Dashboard、profile GET 的缓存延迟、读回列表排序和同 TG 不同 slot 行为，均需 mock 之外的受控验证。
- 单呼动态链接、Drop QSO 的确切路由范围，以及 Private Call 4000 在 4602 上的动作语义，未在本轮 BM 官方文档中闭合。

后续做 live/HIL 时，先用 mock 验收请求计划；由操作者明确提供并单独保管 v2 API key。逐项手工添加和读回静态 TG，确认 slot、服务端流量仲裁，再验证一通测试 Quick Call 与 TG4000 清理。每一阶段单独记录 API response、profile readback、BM Dashboard 状态、Native DMRD 统计和人工听音；不能把其中一项替代其他项。
