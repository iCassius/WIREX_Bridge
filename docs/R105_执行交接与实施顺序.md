## 尚未接入运行链

- Native 当前仍使用原 pipeline 和主/次过滤器；`talkgroup_routing` 尚未接入 `Receiver::ingest`、WinMM、HRI T0 或音频生命周期。
- 当前 UI 控制管道只处理 Q/EOF 停止命令。IPC v2、policy 更新命令和新配置 schema 尚未实现。
- API mock 只验证请求计划、安全裁剪和固定响应下的状态处理；没有 live transport，也没有 BM 服务端读回证据。
- WPF 真实多路卡片、RX policy/TX target 独立控制，以及与 Native 状态联动尚未完成。
- 没有执行 BM Quick call、设备音频、PTT、RF 或 HIL 验证。API 的 99 条 mock 断言不能替代这些结果。
- R105 本轮以 `main` / `71a45c7` 为提交基点；变更不触及 alpha.4 tag、资产、manifest 或本机运行指针。

## 后续实施顺序

1. **IPC v2 与 schema migration**：先冻结 run/request ID、revision/CAS、命令去重、事件字段和 v1 Q/EOF 兼容；迁移旧配置时保留 Selected 单路监听语义，校验完整对象后再替换。
2. **Native pipeline 仲裁**：把 DMRD/LC 验证、本地策略和单 owner 仲裁放在 `Receiver::ingest` 前；接入 RX/TX lease、generation、拒绝旧帧、PCM/WinMM 清理和 HRI stop 确认。用 fake HRI ack 验证清理完成前 owner 仍 busy，且不播放陈旧队列。
3. **WPF 按钮与状态**：用 IPC v2 状态显示候选、Selected/AllDelivered、本地组/Source ID 屏蔽、独立 TX 目标和订阅 readback。UI 必须区分本地允许、远端静态读回、动态请求/确认/到期；当前 lease 与下一 TX 目标也分开显示。
4. **BM live transport 与 QuickCall 最后实测**：先让 API schema、读回 scope/freshness、凭据隔离和 mock 交叉审查冻结，再实现需显式启用的 live transport。Quick call 只能由用户明确操作触发，权限或 media owner 检查失败时拒绝且不排队。软件闭环审查后再单独安排受控 BM/设备实测；`accepted` 仅表示本地接收请求。

每一步先提交可审查源码和对应离线测试证据，再进入下一步。只有 IPC、pipeline、WPF、API transport 和受控设备验证分别完成后，才讨论新 release；在此之前继续保持 alpha.4。
