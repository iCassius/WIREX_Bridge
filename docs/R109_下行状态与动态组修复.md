# R109 下行状态与动态组修复

## 结论

R109 修复了一个边界情况：BM 已准入一个下行呼叫，但该呼叫在 EOT 或 360 ms 接收看门狗结束前没有收到任何有效语音 burst。此前协调器会在收到 `receive_started` 后立即启动 HRI T3；如果网络呼叫随后以零语音结束，HRI 会经历空播放排空并进入 T0 收尾。现在协调器等到至少一个有效语音 burst 已进入接收管线后才启动 HRI。零语音呼叫结束时，协调器跳过 T3，取消该接收代并执行原有的无 HRI 音频清理，之后释放 Router owner。

这是“无语音呼叫不触发播放”的修复切片，不能据此把 TG91 的所有断开情况归因于空呼叫，也不能据此解释鹦鹉回放为何显示红 LED。用户对旧版 `local-hri-downlink-0304eff` 的现场对照同样观察到红 LED；因此红 LED 不是 alpha6 新增 source ID overlay 才出现的问题。LCD 身份功能仍保持启用。

## 实现

- `Snapshot` 新增当前接收代已接受并入队的有效语音 burst 数。每个新 `call_started` 将计数清零，后续只在协议层产出有效 voice 事件且媒体成功入队时增加。接收结束、取消及启动超时事件也携带该计数。空闲快照可能保留上一代的计数；判定函数先检查接收状态和 generation，所以空闲快照返回 `inactive`。调用方只应把计数解释为当前接收代的值。
- `receive_hri_start_decision()` 是 probe 和离线测试共用的门控。尚未收到语音时返回 `wait_for_voice`；有效语音已到时允许启动；零语音网络结束时返回 `discard_empty_ended_call`。这避免测试自行复制另一份条件判断。
- `begin_stream_for_pending_rx` 在 T3 前检查共用判定。`network_ended` 事件发现零语音且 HRI 尚未开始时，清除 pending 标记并调用 `cancel_rx()`。已有的 `receive_cancelled` 清理分支完成 WaveOut 清理、上报 routed RX cleanup，并在清理成功后释放 Router owner。诊断字段保留网络原始结束原因；随后收到取消事件不会把 `terminator` 或 `watchdog` 覆盖成 `cancelled`。
- 接收启动期限仍为 3 秒；DMR 接收看门狗仍为 360 ms。首个 burst 到达前的接收缓冲和晚 LC 确认路径没有改写。source ID overlay、默认 LCD 身份行为、Router half-duplex owner 序列和 EOT/watchdog 规则均保留。
- JSONL 状态现在报告 `rx_call_end_reason`、`rx_call_missing_packets` 和 `rx_call_accepted_voice_bursts`，用于区分终止类型、缺包量和该接收代实际接受的语音数量。

## 离线回归

Focused MSVC 编译通过：`src/bm_voice_pipeline.cpp`、带 `WIREX_ENABLE_BM_BRIDGE` 的 `src/probe_main.cpp`、`tests/bm_bridge_loopback_test.cpp`、`tests/bm_routing_lifecycle_test.cpp` 和 `tests/bm_voice_pipeline_test.cpp`。复用先前构建目录的 upstream/core 对象，只重编受影响对象并链接三个 focused 测试；没有运行 full builder 或全量 39 项测试。

通过的离线测试：

- `bm_bridge_loopback_test`：经本机 fake Master 的 localhost UDP、真实 DMR/AMBE 管线和 synthetic HRI/audio sink 验证。header-only 呼叫在 EOT 和 watchdog 结束时都不产生 T3/T0；清理后 Router owner 回到 idle。接着的一通一 burst 呼叫在 EOT 先于 HRI T3 记录确认时仍保留首 burst，确认后完整送入 fake sink、收到模拟的播放完成 ACK，再发 T0。测试同时确认 T3 的 source ID 与被准入呼叫一致。
- `bm_routing_lifecycle_test`：验证 voice sync 与晚到 LC 确认之间不打开 HRI gate；LC 确认后有效语音计数、source ID 和 gate 状态一致，并沿用既有的 Router drain、stop、cleanup 生命周期。
- `bm_voice_pipeline_test`：接收快照、媒体队列、路由及播放 ACK 的既有离线回归通过。

测试只使用 localhost fake Master、合成 HRI 记录和内存音频 sink；没有打开 COM、真实音频设备、真实 BrandMeister 连接、PTT、RF 或官方电台软件。尚未运行 full 39 项构建/测试、package/UI 验收或真实设备验证。

## alpha6 日志与 LED 证据边界

已检查 alpha6 的结构化运行日志，未读取密码或连接配置中的凭据。该次日志包含 6 个已准入下行呼叫：2 个私有 Echo 回放和 4 个 TG91 组呼；六次均记录了 `bm_receive_ended`、`bm_receive_playback_drained`，随后记录 `rx_waveout_reset_and_hri_t0_cleanup_completed`。接收播放期间没有记录 `ptt_gate_tx_active`，BM session 保持 ready，日志内的 `radio_state` 为 `unknown`。日志没有可用于确认 LED 颜色、实际 HRI 发射状态或射频行为的证据。

当前和历史源码比较发现，alpha6 默认构造了带 `ID<source>` 标签的单次 T3 候选，而更早版本默认使用原候选；但用户报告更早的 `local-hri-downlink-0304eff` 也显示红 LED。因此这项差异不能解释红 LED。未删除或禁用 LCD source ID 功能。

独立静态证据指出官方 FUN10011ea0 的 `+0x50` 字段写入 `1/2/4/8`，另一个调用点将其记录为 Text/Picture/Voice/Emergency List request。尚未闭合两个函数是否操作同一对象及相同上下文，也未建立该字段、HRI 下行音频和 LED 颜色之间的设备语义。不能从 T3/T0 字节或本次离线日志推断蓝/红 LED、PCM 是否实际播放或射频是否发射。下行 LED 原因仍待官方对象调用路径证据和受控实机验证。
