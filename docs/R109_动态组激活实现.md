# R109 动态组激活实现

## 目标与边界

本切片把“加入本机收听”和“激活动态组”实现为两个互不替代的显式操作。前者只更新本机 `rx_policy`；后者发送一次无语音 DMR Quick Call，不调用 BM 静态组订阅 API，也不更改本机接收规则、下一发射目标或语音发射许可。

该功能按 R105 的 BM 订阅研究、R105 核心架构和 R108 当前运行路由接口实现。SharkRF openSPOT3 的 [Homebrew/MMDVM Quick Call 手册](https://manuals.sharkrf.com/openspot3/en/side-panels-tools-page.html#quick-call)说明，短空呼叫类似短按 PTT；短组呼可以连接指定 TG，TG4000 则是断开控制。手册没有规定每台 BM Master 接受 Quick Call 所需的最少帧数，也没有给出 BM China 4602 的驻留时间。因此这里仅把两帧 UDP 发送完成报告为“激活请求已发送”，不报告 BM 已确认加入或会保留多长时间。本轮访问 BrandMeister 的 [Dynamic vs Static 说明页](https://help.brandmeister.network/talk-groups/dynamic-vs-static/)时收到 HTTP 403；这只是该说明页的访问结果，不能据此判断 API Manager 或 BM 接口是否支持动态组写入。

## 用户操作与界面

主界面新增 TG 输入、TS1/TS2 选择和两个按钮：

- “加入本机收听”将输入的 `(TG, TS)` 加入本机 RX allow 规则；若同一项被本机规则屏蔽，则在同一策略更新中解除该项屏蔽。它只发送 `rx_policy.replace`，不会发送 BM 网络 Quick Call。
- “激活动态组”发送一条 `network_subscription.quick_call_join` 控制请求。它只发送 Quick Call，不修改 RX allow/block、TX target 或 `transmit_enabled`，也不授予语音 TX lease。

TG 必须是 1 至 16777215 的整数，时隙必须为 TS1 或 TS2；TG4000 被拒绝，因为它是断开动态组的控制目标。生产界面只有在本次运行的 Native 控制能力已确认、BM 状态仍为 `ready`，且 Router、BM pipeline、HRI stream 和清理流程均空闲时才启用相应操作。TG91 与 TG46001 仍受保护，不能用作语音 TX 目标；二者可以作为无语音动态组激活目标。

当前语音发射目标（已锁定）与下一发射目标使用不同标签和位置显示。小窗口下保留当前目标及其冻结值，不会把它与下一目标混为一项。运行页不显示动态组倒计时，也不把“请求已发送”改写成“已加入”。

## Native Quick Call 与 IPC

`wirex::quick_call::make_group_plan` 使用当前连接的 Source ID、Gateway ID、色码和用户指定的组呼 TG/TS，生成 DMR 组呼 LC header 与 EOT 两个控制帧。它不生成语音 burst，也不调用声码器。当前发送函数用 `dmrd::encode` 把这两帧编码为 55 字节 DMRD 包。测试对两帧分别解码，检查组呼 LC、目标 ID、时隙、stream ID、包类型和无语音 burst 标记；TG91/TS2 的样例 header 与 EOT flags 分别为 `0xA1` 与 `0xA2`。

发送走专用的短时 Quick Call 处理段。处理器先验证本次控制 hello、BM session 和 UDP transport 已 ready，并检查 pipeline TX/RX idle、Router media owner idle、没有待释放的 PTT、HRI stream idle，且没有待处理的 RX/TX cleanup。它创建唯一 stream ID，将本次两帧和目标冻结在 `active_quick_call_plan` 中；outbound drain 只把与冻结计划下一帧完全相符的数据报视为这次控制帧。控制帧成功发到 UDP 后分别记录 header/EOT 发送结果，不增加语音 TX 统计，不创建持久 Router 语音 lease，也不触碰语音 TX 许可或目标。

Dispatcher 在 callback 之前检查并记录 `request_id`，同一请求重放会返回已缓存结果，不再调用发送器。严格校验仅接受 `{group:{destination_id,slot}}`，拒绝零值、超界、TS0/TS3 和 TG4000。只有 header 与 EOT 都经过 transport 发送确认后，结果才返回 `activation_status=request_sent`、`frames_sent=2`。零帧失败返回发送失败；仅 header 已发、EOT 未发时，协议响应只返回 `quick_call_partial_send`，不包含已发送帧数。Native 发送日志记录 header 已发送和 EOT 失败；按该固定两帧计划，这一部分发送路径只发出一帧。两种失败都不会自动重试；用户检查连接后再次点击会创建新的请求。

发送成功只证明本机 UDP transport 接受并发送了两帧。它不证明 BM 已经把动态组链接到本设备，也不证明用户随后能收到该组语音。后续 BM 来话和本机 RX 路由各自由现有状态通道报告。

## 隔离诊断与验证

`--routing-diagnostic` 的特殊验收回调不创建 BM socket、不打开真实 transport，也不伪报 BM ready。它调用同一个 `make_group_plan` 和 `send_once`，将产生的两个包送入内存 sink，实际 DMRD encode/decode 后校验 header/EOT、目标和无语音 burst，并核对执行前后完整 routing JSON 相同。诊断快照继续报告 `bm_state=not_started`。该路径只用于测试，不会放宽生产 readiness gate。

WPF 自动验收通过实际主界面按钮事件走 Supervisor 与 Native Dispatcher：本机收听按钮只产生 RX 策略更新；激活动态组按钮产生一条 Quick Call 命令。最终结果记录 TG46001/TS2、两帧、未重放、BM 未连接、source ID 777 屏蔽保留，以及 Quick Call 前后 RX/TX 完整状态未变化。

离线渲染在正常 1180x820 与 1024x728 工作区都通过。样例用当前锁定目标 TG53000/TS1 和下一目标私呼 460997/TS2 验证二者清楚分开；小屏 CurrentCallValue、CurrentCallDetail、屏蔽当前来源按钮、Stop 按钮和动态 TG 两个按钮都在窗口及各自卡片内完整可见。该渲染样例仅用于布局压力检查，不表示 Native 允许同时进行 RX 和 TX。

已运行的验证：

- `dmr_call_test`：DMR 组呼 LC、55 字节 DMRD 往返、两帧计划、首帧失败不发送第二帧、部分发送只报告一帧、readiness 忙/未就绪拒绝、TG4000 拒绝。
- `ui_control_protocol_v2_test`：严格 TG/TS 校验、忙时拒绝、partial-send、同一 request ID 重放不重发，以及 Quick Call 不修改 RX/TX 策略。
- `test-ui-control-v2.ps1`：新七命令 routing diagnostic 通过真实 WPF BridgeSupervisor 与 Native；界面解析器仍接受旧六命令路由核心，Basic control diagnostic 保持三命令。
- `test-ui-routing-diagnostic.ps1`：完整 WPF 实际按钮到 Supervisor、Native Dispatcher 和内存 sink 的隔离链通过。
- `test-ui-render.ps1`：正常和 1024x728 WPF 实际渲染与控件/card 边界检查通过。
- `probe_main.cpp` 使用 MSVC `/c` 编译通过；临时诊断 exe 使用 R109 重新编译的 probe、BM pipeline 与 UI control protocol 对象链接，复用 alpha6 同源 core/codec 对象。

以上都是本机离线或内存测试。没有调用真实 BM、读取密码或 API key、打开真实 COM/音频设备、发送真实 UDP/RF、运行全量 39 项构建测试或执行 HIL。最终合并后的 full39 与 alpha.7 package 验收由集成阶段另行完成。

## 变更文件

- `include/wirex/quick_call.hpp`：Quick Call 计划、readiness helper、一次性发送和 DMRD 对比辅助函数。
- `include/wirex/ui_control_protocol.hpp`、`src/ui_control_protocol.cpp`：独立 callback、七命令能力报告、严格输入与重放缓存语义。
- `src/probe_main.cpp`：运行时 Quick Call readiness gate、冻结帧识别和发送结果；routing diagnostic 内存 sink。此文件中的 RX empty-call/start gate 属于 R109 下行修复切片，见[下行状态与动态组修复](R109_下行状态与动态组修复.md)。
- `tests/dmr_call_test.cpp`、`tests/ui_control_protocol_v2_test.cpp`：协议帧与 Dispatcher 单测。
- `ui/windows/MainWindow.xaml`、`ui/windows/bridge-ui.ps1`、`ui/windows/BridgeSupervisor.cs`：输入、双按钮、状态文案、控制能力与结果映射、自动验收链和小窗口布局。
- `tools/test-ui-render.ps1`、`tools/test-ui-control-v2.ps1`、`tools/test-ui-routing-diagnostic.ps1`：布局、旧/新能力兼容和真实 UI 按钮链离线验收。
