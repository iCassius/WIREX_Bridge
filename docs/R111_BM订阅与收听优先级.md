# R111 BM 订阅与收听优先级

**研究日期：2026-10-29**

**代码基准：`app` 仓库 HEAD `d2c0984`**

**范围：DIRECT 模式的 DMRD 收发、BM 动态/静态组订阅、本机 RX 仲裁。本文只记录代码与官方文档研究，不进行 BM 登录、API 请求、Quick Call、音频/PTT/COM/HRI 操作。**

## 结论

1. DIRECT 的 BM 语音数据仍按 DMR timeslot 编码。发送端从 profile 的全局 Color Code 和本次呼叫的 TS 生成包；接收端能从 DMR LC/embedded signaling 识别并显示 CC，但本机 RX 路由当前按 TG、TS、呼叫类型和来源 ID 匹配，不以 CC 过滤。TS1/TS2 可识别；当前没有每条路由单独设置 CC 的能力。
2. R109 动态组激活发出的是一组 DMRD group-call header 与 EOT 控制帧，没有语音 burst。openSPOT3 官方手册明确说空 Quick Call 会显示在 BrandMeister Dashboard。用户此前观察到 BM 网页出现一次呼叫与该说明一致。BM 网站以外的其他终端是否也显示该记录，现有资料没有给出答案。
3. 本轮没有在 BrandMeister 官方文档找到“不发 DMR 呼叫、直接临时添加动态 TG”的 REST endpoint 和 schema。官方 API Manager 页面展示的是静态组编辑与丢弃当前 QSO/动态组；其中 `Drop All Dynamic` 是清理动作，不是添加动态组。允许持久服务器配置的场景可考虑显式添加静态订阅；这会改变远端配置，且不等于动态加入。
4. 多目标策略表示本机可接纳哪些已收到的流，不是混音器或音频优先级队列。BM Master 决定将哪些上游流转发到本节点；Native 只能调度已经收到的数据报。当前 Native 单一媒体 owner 按当前管线准入条件接纳一条匹配策略的新流，持续到 EOT、播放 drain、WinMM/HRI 清理和 T0 收尾完成。语音同步可能先让某些来话进入活动接收状态，而 `current_call_link_control_validated` 仍为 false；不能把每条已接纳来话都描述为完整 LC 已验证。忙时第二条流会丢弃，不会延后补播或自动抢断。
5. 本轮不改动这项仲裁，也不增加优先级字段。默认当前呼叫保持现有行为。未来可设计一个短暂窗口，收集已收到的新来话候选，校验候选有效性，把原始帧放入有容量上限的缓存，再按用户顺序选一条来解码播放；这种方案未必需要同时运行多个语音解码器。设计还需确定窗口带来的起播延迟、活动呼叫是否允许被打断及恢复规则。任何本机规则都只能选择已由 BM Master 转发到本机的流。

## 4. DIRECT 下 TS1/TS2 与 Color Code

这里的 DIRECT 是本软件通过 BM Homebrew DMRD 传输连接到 FTX-1 DIRECT HRI 的路径，不是声称 C4FM RF 或 DMR RF 空口正在工作。

| 项目 | 当前代码行为 | 代码位置 |
|---|---|---|
| DMRD 时隙 | DMRD flags 的 `0x80` 表示 TS2，否则 TS1；组呼/私呼由 `0x40` 区分。收包转换将时隙写入呼叫身份。 | [`dmr_call.cpp`](../src/dmr_call.cpp#L68-L72)、[`bm_voice_pipeline.cpp`](../src/bm_voice_pipeline.cpp#L1312-L1327) |
| 发送 Color Code | 呼叫配置中的 `color_code` 用于编码 voice burst 和 LC/slot signaling；`CallConfig` 有 CC 值，但 UI/profile 是连接级全局设置。 | [`dmr_call.hpp`](../include/wirex/dmr_call.hpp#L51-L58)、[`dmr_call.cpp`](../src/dmr_call.cpp#L193-L208) |
| 接收 Color Code | RX 解码器在完整 LC 或有效 embedded signaling 后记录已知 CC；状态可提供给 UI。来话的活动状态与 `current_call_link_control_validated` 分别记录；某些 voice sync 接收路径可在 LC 仍未验证时先接受来话。 | [`dmr_call.cpp`](../src/dmr_call.cpp#L399-L420)、[`dmr_call.cpp`](../src/dmr_call.cpp#L583-L590)、[`probe_main.cpp`](../src/probe_main.cpp#L4979-L5048)、[BM 来话身份显示](BM来话身份显示.md#核心处理) |
| 路由匹配 | Receive filter 比较 destination、可选 TS、呼叫类型和可选 source ID，不比较 CC；Router 的活动呼叫身份也没有 CC。 | [`bm_voice_pipeline.cpp`](../src/bm_voice_pipeline.cpp#L1298-L1305)、[`talkgroup_routing.cpp`](../src/talkgroup_routing.cpp#L601-L609) |
| Quick Call | 使用当前 profile 的全局 CC，并使用显式请求的 group 和 TS 产生 header/EOT。 | [`R109 动态组激活实现`](R109_动态组激活实现.md#L20-L28) |

所以可确认 Native 能标出 DMRD TS1/TS2，并将解出的 CC 状态显示出来；不能据此说每条 Direct RX 路由都按 CC 过滤。DMRD 外层 header 本身携带时隙和 call kind，没有在本项目路由入口中承载 CC 过滤字段。BM API 文档的设备 `slot` 参数是 API 设备槽位；不要将其与 DMR TS1/TS2 混为一谈。[R105 BM 订阅研究](R105_BM订阅控制研究.md#L56-L60)

官方 MMDVM-Host 源码也将这些层分开：`DMRNetwork.cpp` 由 DMRD flags 的 `0x80` 读取/写出 slot 2，由 `0x40` 读取/写出 group/private 类型；`DMRSlot.cpp` 在重建 EMB 时写入配置 CC，并在 late-entry 中检查 EMB CC。它描述 MMDVM 的 DMR 网络/RF 处理，不定义本项目的 HRI 或 BM API 行为。本文引用 2026-10-29 可见的源码版本，revision `9384d683c9993f67af52b062b1bf9d4df11b6446`：[`DMRNetwork.cpp` L1171-L1237](https://github.com/g4klx/MMDVM-Host/blob/9384d683c9993f67af52b062b1bf9d4df11b6446/DMRNetwork.cpp#L1171-L1237)、[`DMRNetwork.cpp` L1241-L1336](https://github.com/g4klx/MMDVM-Host/blob/9384d683c9993f67af52b062b1bf9d4df11b6446/DMRNetwork.cpp#L1241-L1336)、[`DMRSlot.cpp` L3486-L3524](https://github.com/g4klx/MMDVM-Host/blob/9384d683c9993f67af52b062b1bf9d4df11b6446/DMRSlot.cpp#L3486-L3524)、[`DMRSlot.cpp` L3541-L3552](https://github.com/g4klx/MMDVM-Host/blob/9384d683c9993f67af52b062b1bf9d4df11b6446/DMRSlot.cpp#L3541-L3552)。

## 5. 动态组激活：网页记录、其他终端与无呼叫路径

### Quick Call 的可观察结果

R109 只允许核心 ready 且 TX/RX、Router owner、HRI stream 和清理状态都 idle 时响应明确的 `network_subscription.quick_call_join`。Native 为目标创建唯一 stream ID，发送 group-call header 和 EOT；没有语音 burst。只有两个 UDP datagram 都由本机 transport 成功发送后，返回 `request_sent`。这表示本机已发送控制包，不是 BM 已确认组已链接。重复 `request_id` 会返回缓存结果而不会重发；TG4000 仍被拒绝。[R109 实现记录](R109_动态组激活实现.md#L22-L28)

SharkRF openSPOT3 厂商手册说明 Quick Call 是类似短暂按下 PTT 的空 call，BM Dashboard 会显示这些 empty calls；短组呼会动态链接 TG。[Quick Call / BMM 手册](https://manuals.sharkrf.com/openspot3/en/side-panels-tools-page.html#quick-call) 和 [DMR usage notes](https://manuals.sharkrf.com/openspot3/en/dmr-usage-notes.html)（厂商设备文档，不是 BM 官方 API 规范）。这与用户观察到动态激活后网页显示一次呼叫相符。文档没有说明 BM Dashboard 以外的每一种 DMR 终端或监听软件会怎样展示；现阶段应将其记为未知，不能断言只有网页显示或所有终端都显示。

### 是否存在静默添加动态组的官方 REST API

BrandMeister 官方 [API Manager 文档](https://help.brandmeister.network/hotspots/api-manager/)列出静态组 Add/Delete、Drop QSO 和 Drop All Dynamic 操作。该页称界面可以查看当前 Static/Dynamic TG；没有发布静默添加动态组的 REST endpoint/schema。BrandMeister 官方 [User API key 说明](https://news.brandmeister.network/introducing-user-api-keys/)只概述应用可以读写账号数据（包括静态 talkgroup 配置），不是完整 API endpoint 规格。基于本轮可查到的官方文档，不能声称有一个无需 DMR Quick Call 的动态组加入接口；这不证明服务器内部或未公开资料不存在其他做法。

特别注意，本仓库 [`bm-subscription-api.psm1`](../tools/bm-subscription-api.psm1#L196-L252) 的动作枚举为 `ReadProfile`、`AddStatic`、`RemoveStatic`、`DropDynamic`、`DropCallRoute`，没有 `AddDynamic`。`DropDynamic` 的实现是 GET 清理 action，而不是添加组。该模块的静态 endpoint/body 和 `ReadProfile` 字段部分来自 R105 中标明的第三方客户端观察，不应作为 BM 官方 OpenAPI 定义引用。

### 可选做法

| 目标 | 做法 | 代价与边界 |
|---|---|---|
| 临时动态链接，接受网页出现空呼叫记录 | 保留显式 Quick Call。界面应继续标为“请求已发送”，不能显示“已加入”。 | 会发出 DMR 呼叫控制帧；BM Dashboard 显示空 call 有厂商文档佐证。其他客户端展示方式未知。 |
| 不发 DMR 呼叫，且长期/定期接收目标组 | 由用户明确配置静态订阅（设备 Dashboard/API 管理路径），本机 RX 仍只播放所选目标。 | 会写入 BM 远端配置并维持静态订阅；这不是动态临时加入。本仓库 API module 尚未接入正式 UI/transport，不能在当前 UI 中实际执行。 |
| 不发呼叫、不改 BM 配置 | 不触发订阅；仅被动播放本节点当前已经从 BM 收到、且通过本地 filter 的流。 | 未被服务器转发的动态组仍无法收听。 |

本轮推荐保持显式 Quick Call 用于“临时动态加入”，并把“静态订阅”留作需要持久流量转发时的显式用户配置选项。没有依据将它们合成一个静默动态 API 操作。

动态超时需按服务器区分：BrandMeister 官方 [Dynamic vs Static](https://help.brandmeister.network/talk-groups/dynamic-vs-static/)说明 USA Master 动态组按 15 分钟超时，并明确其他 Master 依其配置。该 15 分钟不能套用于 BM China 4602，也不能推导 4602 的动态续期时间。该官方页面关于活动方式的说明也将动态 activation 描述为终端用户经 repeater/hotspot 的 PTT 激活；本软件 Quick Call 属于此类 DMR 呼叫行为，不是 API 静默编辑。

## 6. 多组收听和本机仲裁边界

必须分开看两个仲裁点：

1. **BM 上游转发**：节点只会看到 Master 发到当前 Hotspot/Repeater 的 DMRD 数据报。静态 TG 数量、同一时隙来话竞争与 Master 的转发规则发生在上游。BrandMeister 官方[静态组帮助](https://help.brandmeister.network/repeaters/sysop-dashboard/static-talkgroups/)提醒，同一时隙配置很多静态组时，繁忙组可能占用该时隙。代码没有设置 BM Master 对不同 TG 的服务端优先级，也不能要求服务端送来它没有转发的包。
2. **Native 本机播放**：允许策略是本机筛选集合。`GroupRoute` 的键是 `(destination_id, slot)`；Receive filter 另可选 call-kind/source 约束。符合当前管线准入条件且匹配策略的新流在 owner 空闲时取得唯一 RX generation；后续包必须属于当前活动 stream。LC 校验是独立状态：语音同步可以先使某些来话进入活动接收状态，而 `current_call_link_control_validated=false`，因此不能笼统声称每条准入流都有完整 LC 验证。[R107 路由状态](R107_运行时路由与仲裁.md#L30-L40)、[BM 来话身份显示](BM来话身份显示.md#核心处理)、[`Router::admit_rx`](../src/talkgroup_routing.cpp#L212-L257)。自然 EOT 后先 drain 当前流 PCM 和播放 ACK，再执行 stopping/WinMM/HRI 清理；外层确认相应 HRI T0 清理后才释放 owner。[`Router::rx_network_eot`](../src/talkgroup_routing.cpp#L273-L300)。

owner 被占用时，其他 stream 被判为 busy 并在解码/播放前丢弃；EOT/drain/T0 期间也不接纳下一条流。其间丢弃的语音不会在当前呼叫结束后补播。策略中有多个 allow route 只扩大“本机可接纳哪些已收到的组”，不会形成多流混音或等待队列。[R107 运行时路由与仲裁](R107_运行时路由与仲裁.md#L30-L40)、[R105 多目标架构](R105_多目标核心架构.md#L17-L19)。

本轮不增加按优先级排队、排序或自动抢断的核心功能。未来如要做更偏向单频道的接收，可先评估“关注组模式”：将本地 allow list 限制为单组，并提供清楚的手动停止/释放当前来源操作。此方案只能决定已到本机的数据报如何入流，不能提高 BM Master 的转发优先级。自动优先级则需要同时观察短时间窗口内的多条候选流，至少具备多 stream 的 LC/voice 解码和有界 PCM 缓冲，才能比较优先级；必须显式确定最大等待延迟、活动呼叫是否可被更高优先级流截断、被截断流是否永不恢复及资源上限。未经用户进一步定义和确认，不改变当前 owner / 当前呼叫语义。

## TG91 历史验收和 LED 观察

历史 `ab3c5fa` 的 `listen-91` 预设使用 TS2/CC1；用户将本机 Gateway 的 TS2 TG91 配置为静态订阅后确认实机收听正常。记录没有通话次数或持续时间。[BM 联调推进](BM联调推进.md#L21-L22)。

本轮用户于 2026-10-29 反馈 alpha.8 的 TG91 静态组可以正常收听，但主观音量稍小。本机运行摘要显示有效播放增益为 1.000x、clipped samples 为 0；保存设置中的 `radio_playback_gain=5.959` 没有反映到该次运行。此处只保留排查所需的版本与增益摘要；原始运行日志和个人音量配置留在本机，不列出路径或内容。alpha.8 的用户反馈和运行摘要分别记录，不与 `ab3c5fa` 的历史听音或 alpha6 的六通下行日志合并成同一验收。alpha6 中的 TG91 统计与 LED 观察仍按下一段单独记录。

R109 alpha6 结构化日志记录 6 个已准入下行呼叫（2 个 Echo、4 个 TG91），每次都记录 BM receive end、playback drain 和随后 HRI T0 cleanup；没有记录 `ptt_gate_tx_active`，`radio_state` 是 `unknown`。[R109 下行状态](R109_下行状态与动态组修复.md#L31-L35)。用户曾报告 alpha6 和更早的 `local-hri-downlink-0304eff` 出现红色 LED；红灯观察予以保留，但现有日志没有记录 LED 颜色，也没有确认 HRI 发射或 RF 状态，不能把红灯作为 BUSY、PTT 或 RF 活动的证明。

## BM API planner 与 UI 接入现状

- `tools/bm-subscription-api.psm1` 是离线请求规划/验证模块。`New-BmApiRequestPlan` 有 `AddStatic`、`RemoveStatic`、`ReadProfile` 及清理 action，没有 `AddDynamic`；`New-BmStaticReconciliationPlans` 只计算静态订阅差集。
- `Invoke-BmApiRequestPlan` 要求调用方注入 `Transport` scriptblock，仓库没有给它配置实际 BM HTTP transport；模块及相关 fake transport 工具没有从当前 `ui/windows/bridge-ui.ps1` 导入或调用。
- UI 当前注册的网络订阅命令只有 `network_subscription.quick_call_join`；点击后经 IPC 请求 Native 发短 Quick Call。UI 不提供 BM 静态订阅 API 管理入口，也没有显示静态 profile readback。
- 所以当前可用 UI 控制的是明确的短 Quick Call。静态添加只是离线计划能力和研究材料，不是已完成的可操作功能。若未来接 API，需要先取得并验证 BM 官方或维护方当前 endpoint/schema，取得用户明确确认后再写入服务器；不应借用 `DropDynamic` 伪装成 `AddDynamic`。
