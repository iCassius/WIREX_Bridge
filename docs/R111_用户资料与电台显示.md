# R111：DMR 用户资料与电台显示边界

日期：2026-10-29。研究目标为 DMR Source ID 的呼号/用户资料查询，以及将呼号作为 HRI 电台显示候选。WIRES-X 证据限于版本 2.0.1.0 的固定 PE/DLL 静态记录；本轮没有运行官方程序、连接 COM/音频/BrandMeister、操作电台或触发 PTT/RF。

## 官方 RadioID 查询与数据使用

RadioID 的公开 API 文档说明普通单条查找可以使用；页面列出 `/api/dmr/user/` 和 `/api/users`，并支持按 `id`、`callsign`、`name`、`city`、`state`、`country` 等字段过滤。API key 当前为可选项，页面建议新集成准备 `X-API-Token`。同一页面要求自动化客户端以清楚的 `User-Agent` 标出应用名和联系地址，并说明公开镜像、批量导出、可复用数据库、公共 feed 或竞争目录需要书面许可。见 [RadioID Database API](https://radioid.net/api/)。

本轮浏览器无法读取该页面链接的完整 API Use Policy 和文本版本，二者都返回浏览器验证页。可访问的 `/api/` 页面没有公布缓存 TTL；因此下列 TTL 是 Bridge 的本机缓存策略，不是 RadioID 要求。

建议运行路径按 Source ID 每次最多发送一个显式查询，不向 RadioID 自动上传每通来话者 ID。后台音频/来话处理只读本机缓存。用户点击“查询资料”后，UI 才发起单 ID 请求；请求需设置清楚的应用 `User-Agent` 与联系地址、有限超时，失败时不自动重试。不得在 Bridge 内自动下载全库或将全量目录放入便携包。

本机缓存保存在当前 `UserConfigDirectory` 下的 `radio-identity-cache.json`，不写进 Git 或通用发布包。alpha.9 UI 只在用户点击“查询资料”后发起单个 ID 请求；缓存读取放在来话与音频热路径之外。可先采用正记录 30 天、未命中记录 24 小时的本机 TTL；过期条目标记为 `stale`，不自动续查。查找失败时保留数字 DMR ID 标签，并可显示注明来源和时间的缓存呼号；数字 ID 不能被表述为 RadioID 返回的真实呼号，也不承担设备身份认证。RadioID 页未提供 TTL 时限，实施者可按后续 API 使用条款再调整。

## 官方 WIRES-X 身份字段与 HRI 头部

官方 EXE `FUN_004bdb50` 从 `USER_INF` 读取 `CallSign`、`CityName`、`StateName`、`Country`、`ID_No`、`SvNodeID`、`User_RadioID` 等**本机资料**。`FUN_004e5580` 从这些全局值构造 D/E 文本；静态映射将 `DB` 接到 `ID_No`、`DC` 接到本机 `CallSign`，`DE` 与 `E1` 接到本机 `User_RadioID`。`SetDigiTrcvData(0, ...)` 将 D/E 文本放入 HRI 对象队列，HRI 对象随后可将输出记录交回主程序，主程序路径之一再把缓冲区和长度交给 `WriteFile`。这些记录证明 PC 客户端会把本机资料送入 HRI 软件路径；它们没有把 `CityName`、`StateName`、`Country` 标成电台 LCD 字段，也没有把本机资料连到当前 BM 远端发话者。证据：EXE `FUN_004e5580` `ev_5131b0c70d73a5f6b72c69e23fb4ff735ce3e5d673ac8d5c9bd16a32e39d8ef9`、`FUN_004bdb50` `ev_69c0d7a75eeb03b5c49eed4754457f21bde1e9eea5b38a659ed5a88df7b9afa9`、`SetDigiTrcvData` `ev_5a1c56f443db2913fbc51c4d24d7b930ea3e428f8a41e82b1f831a64e7118d8c`。`WriteFile` 路径及限制见 [WIRES-X 屏幕与路由软件研究](WIRESX屏幕与路由软件研究.md) R77。

HRI 的另一条 G 记录路径会从记录节点 `+9` 复制连续 68 字节到头部缓存。HRI 随后从头部读取目的呼号 `+8..+0x11` 和源呼号 `+0x12..+0x1b`，各 10 字节，并以 `DestCallSign` 与 `Src CallSign` 记录；HRI 本机呼号单独位于 `+0x1c..+0x25`。本机 Node Radio ID 编码另占 `+0x30..+0x34` 五字节。HRI 的非空 T 记录构造函数会复制填好的 68 字节头部到 T 正文，之后再处理正文数据。`FUN_10014b50` 把生成的 T 正文交给 `FUN_1000b130` 包成内部 T 类型记录并加入 HRI 队列；队列泵在 T 分支把记录指针与长度通过窗口消息 `0x618` 交给 EXE，EXE 路径再把相同指针和长度传给 `WriteFile`。这些静态步骤描述厂商软件会怎样整理和传递一条 T 记录，不确认 `WriteFile` 的句柄一定对应目标 COM、FTX-1 收到记录或屏幕显示字段。证据：G 头部复制 `FUN_10014330` `ev_dd4741e6a283be5d7a5c88c8e35f4a98f22825de30ac56f6d3e015d8ee702ad9`、呼号读取 `FUN_10014070` `ev_af377ccbc045e89e9964c53d4ab86c39d7534f358fda167ec8bf64bfc7435d28`、T 构造与队列 `FUN_10014b50` `ev_0b9ed8732ace5fbca14b93278f85c286ae2354053325a9da2b7c36b1e0c320b4`、队列到写入摘要 `ev_197da0b900013b8b5a094d9c97889641cbeee1c540e7f5c637e4983435051c4d`。

上述来源/目的呼号字段由官方 HRI 代码用于缓冲处理，不能写进 Name 或 City 后就推断电台会显示它们。它们也没有包含 BrandMeister Source ID 的编码映射。当前 Bridge 将数字 DMR Source ID 作为呼号未知时的标签回退；这个数字标签不是 RadioID 返回的真实呼号。本轮没有修改现有串口写入行为。

## 呼号显示实现路径（待实机确认）

基于已定位字段，实现路径限于把用户显式 RadioID 单 ID 查询返回的呼号放入 HRI 头部 `Src CallSign` 十字节槽；输入必须经过 ASCII 和宽度校验。Name、City、State、Country 没有已定位的 HRI 头部字段，不写入未命名的头部偏移。UI 始终保留原始 DMR Source ID，并注明呼号来自 RadioID 映射。是否能在 FTX-1 屏幕看到该字段仍待实机确认。

静态路径只证明厂商 DLL 会解析 68 字节头部并构造 T 记录；它没有证明 FTX-1 收到该记录、LCD 选择该字段显示，也没有证明当前 90 字节空头 T3 候选会被固件按同样方式处理。已有 [HRI LCD 呼号字段候选](HRI_LCD呼号字段候选.md) 是单字段候选研究，不是设备验收。本轮 `lcd_source_identity.display` 仍应保持 `unknown`；必须等独立的受控设备观察后再写成已显示。

## 交接契约

身份查询应由当前接受的来话 `source_id` 驱动，不能取本机配置的 `USER_INF/CallSign` 代替。解析结果可统一为：`source_id`、`callsign`、`name`、`city`、`state`、`country`、`source`、`fetched_at_utc`、`status`。状态建议为 `found`、`not_found`、`stale`、`unavailable`；呼号缺失、查询失败或来源不可用时，UI 显示 `DMR ID <source_id>`。解析与缓存读取放在媒体/来话热路径之外，网络查询只由用户明示触发。RadioID 返回的呼号是资料库匹配结果，不是无线电设备身份认证，也不应改变音频、目标选择、RF 路由或 PTT 状态。

## 未闭合事项

- 没有受控设备结果证明 `Src CallSign` 十字节进入 FTX-1 LCD；实机 LCD 和清屏状态仍未知。
- 没有证据证明 Name/City/State/Country 可由当前 T3 路径送到电台显示。
- RadioID 完整使用条款页和文本版本在本轮浏览器中触发验证页，因而没有确认可访问条款里是否存在缓存 TTL 约束。
- 本轮试图对 EXE 执行额外的 `CallSign` 字符串检索；Ghidra 请求在约 90 秒内未返回，本报告没有将它作为证据。报告引用的静态事实来自此前针对相同哈希样本保存的 R79、R82、R83、R95 与 R110 Evidence。
