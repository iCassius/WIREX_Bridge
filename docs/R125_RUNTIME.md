# R125 运行行为与证据

## 频道激活与运行证据

R125 的“激活组”操作只在用户点击后发出一次 QuickCall 请求。程序按当前设备、频道类型、TG、slot 和 BM 静态组数据检查目标；已识别为静态组的目标不提供动态激活操作。静态 API 查询仍绑定当前设备与 slot 上下文。

如果 Native 状态显示接收或发射仍占用媒体，界面会将这次明确点击排入一个 60 秒队列，并显示取消入口。队列只在同一 run、BM 已连接且 ready、最近 3 秒内有状态、媒体 owner 显示 idle、频道仍存在且未静音时发送一次。到期、取消、停止、重连、断开 BM/串口、频道变更、目标删除或静音都会清除队列。发送时遇到 `media_busy` 竞态会报告失败，不自动重发。

日志只保存白名单字段，覆盖点击、排队、取消、提交、ACK、失败和超时等阶段；每个日志文件最多 256 KiB。一次 `request_sent` 结果表示本机收到了包含两帧发送结果的成功响应。它不能确认 BrandMeister 当前是否仍将该 TG 设为动态组，也不能证明远端已激活。由于各 BM master 的动态规则与时限可能不同，代码不假设或硬编码中国 master 的 TTL。用户可再次点击“再次激活”发起新的明确请求。

对 v0.1.0 运行日志的白名单检查显示，当次 `routing-state.json` 中 TG91、TG46001、TG46021 的 RX allowlist 条目均为 TS2，TX target TG46001 也是 TS2。因此该次运行的配置没有显示 TG46001 与 TG91 使用不同 slot。对应的历史 Native 日志包含大量 TG91 接收记录，但没有 TG46001 接收记录；检查到的 `configDirectory` 下没有 `quick-call-requests.jsonl`。这些历史记录没有点击/提交/ACK 证据，无法判断用户是否点过激活、QuickCall 是否因媒体忙被拒绝，也不能单凭本机状态判断为什么没有收到 TG46001。远端 TG46001 动态激活和接收仍需用户进行实际 BM 联测。

## 音频增益

发射与接收增益使用 1 到 16 的整数值，滑块按 1 递增。内部以 1000 为倍率保存整数。旧范围内的小数配置只在运行时四舍五入到最近整数，超出范围的值在读取后夹到 1 或 16；本次工作没有读取或修改用户实际配置文件。

## 离线验证

- `test-channel-activation-state.ps1`：348 项断言通过；确认开始新请求及 NACK 不会清除同 slot 的旧本机记录，收到有效两帧 ACK 后才替换记录。
- `test-ui-audio-gain.ps1`：92 项断言通过；覆盖整数范围、步进、旧值运行时转换及无效值。
- `test-ui-channels.ps1`：186 项断言通过；覆盖队列生命周期、停止/最后频道删除/断开后不发送、临时 JSONL 白名单阶段、中文来话显示和链接目标。
- RenderOnly 窗口布局验证由 R125 UI 工作项单独执行；该验证没有打开浏览器或访问 BM。

这些检查使用离线合成数据和临时测试配置，没有调用真实 BM、Native 设备、COM、CAT、音频、PTT 或 RF 操作。它们不构成远端激活或无线收发验证。
