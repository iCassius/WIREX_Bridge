# WIREX Bridge v0.1.0-alpha.5（R106 第1步测试版）

## 本步范围

本地测试版实现 UI 与核心之间的 IPC v2 `hello`、`status`、`shutdown` 消息，以及用户配置从 `schema_version: 1` 迁移到 `schema_version: 2`。没有显式选择 v2 的现有启动方式继续使用 v1 的 Q/EOF 停止协议。

配置迁移保留旧配置中的发射目标和单路接收策略。读取 schema 2 复杂策略时，UI 只读展示摘要；保存其他设置时会完整保留这些策略。无法无损表达为旧运行核心单一接收目标的配置不能启动。本步没有多组策略编辑或运行功能。

旧 schema 1 私呼接收目标必须等于 connection.source_id。若旧文件显式设置为其他目标，读取会拒绝迁移并提示修正；读取过程不写回或覆盖原文件。不要把所有 schema 1 文件都视为可自动迁移。

随包 `test-control.cmd` 是无设备协议诊断入口。它启动包内的 `wirex_bridge.exe`，经 stdin/stdout anonymous pipes 执行 `control_ready`、`hello`、`status` 和 `shutdown` 往返；它不连接串口、音频、BrandMeister 或其他网络服务。

## 离线验证

本版构建配置要求保留 alpha.4 原有 35 项 C++ 离线测试，并增加 `ui_control_protocol_v2_test`，总计 36 项。配置迁移、legacy 参数投影、UI 控制管道和渲染检查另有 PowerShell fixture 测试。实际构建结果以本地包内的 `build-provenance.json` 与 `manifest.json` 为准；未完成构建或审计时，不得将候选写成已通过。

## 验收边界

- schema 2 的保存与预览不表示运行核心已实现多组接收。
- schema 2 中无法投影成旧单路接收参数的配置，在核心启动前应被拒绝。
- `accepted`、UI 进程存在或保存的连接配置都不能用来显示真实设备或网络已连接。
- 本步骤没有新增 BM live API、多组音频流水线、quick-call、串口、音频、PTT 或 RF 行为。
- 当前 alpha.5 测试版尚未完成设备/BM 联测。下一步须等用户完成本交接表中的第1步验收。

## 配置与版本

主界面测试使用 `start-step1-test.cmd`，它显式把 `private/r106-step1-test-config` 作为 `UserConfigDirectory`。通用 manifest 审计通过后，本机交付流程会把已批准的 `connection-profile.json`、`audio-settings.json` 和 `password-file-path.txt` 副本放在该目录；密码文件本身不会复制或读取，路径文件只引用原密码文件的绝对路径。这三份个人文件不属于通用包清单，也不应分享。启动器不会搜索、读取或复制其他配置，用户无需手工编辑 JSON。alpha.4 文件夹、启动入口和配置保持独立；alpha.5 测试版不会改写 alpha.4。

schema 2 字段、迁移规则、失败保存行为和用户操作步骤见包内 [`docs/R106_配置迁移与测试.md`](../R106_配置迁移与测试.md)。

IPC v2 的请求字段、序号、去重、EOF 和有界退出规则见 [`docs/R106_IPC第二版.md`](../R106_IPC第二版.md)。
