# R120 BrandMeister API 与 DMR ID 链接研究

**结论（2026-11-01 09:49–09:51 UTC）：** BrandMeister 当前公开的 [API 文档](https://api.brandmeister.network/docs/) 与 [OpenAPI JSON](https://api.brandmeister.network/api-docs?api-docs.json) 均返回 HTTP 200，OpenAPI 标记为 2.1.0，服务根路径为 `https://api.brandmeister.network/v2/`；当前官方 Dashboard 静态资源也返回 HTTP 200，源码内有 API Keys 页面和 `#/profile/api` 路由。当前模块的 Bearer JWT 写入路径和 `{group, slot}` 请求体与规范相符。本文已将静态列表读取及写后读回改为专用 `GET /device/{id}/talkgroup`，并让添加函数接受官方 Dashboard 在 DMO 模式使用的 slot 0。未使用用户密码、真实 API key 或认证请求，未发出 API 写请求；因此用户账户的 key 权限和某台设备的当前模式仍未知。建议第三方管理继续用单独 API key；来话 DMR ID 在呼号未知时保留纯数字，解析出呼号后链接 BrandMeister 的呼号 profile。

## 当前 Dashboard 路由、API key 与登录流程

当前 bundle 的路由表包含 `/profile/api`（自身 API key 页面）、`/profile/:call/api`（呼号 profile 对应的 key 页面）及 `/selfcare`。呼号的 Profile Settings 页有 `API Keys` 按钮；当前官方帮助仍将入口写为呼号菜单 → Profile Settings → Security Settings → API Keys。因此，账户自己的 key 页面直达地址为 [`https://brandmeister.network/#/profile/api`](https://brandmeister.network/#/profile/api)。这次只核对公开 bundle 和帮助页面，没有打开已登录账户，也没有按 Add 或 Revoke。

当前页面文字说明 API key 可供应用管理设备 talkgroup、控制设备连接、修改设备密码及读取设备信息和日志；页面同时说明 API key 不用于 Dashboard 登录或账户管理，并提示更改或重置账户密码不会撤销 API key。OpenAPI 的 `api_key` scheme 定义为 HTTP Bearer，`bearerFormat` 为 JWT。模块目前要求 key 为三段 JWT 字符串且长度至少 200 字节；长度下限是模块本地格式检查，当前 OpenAPI 没有规定这个数值。没有用真实 key 验证服务器会接受某一 key。

Dashboard 登录路径在当前 bundle 中使用 `/api/bootstrap` 并带 `credentials: "include"`，登录表单向 `/api/login` POST 隐藏的 `csrf_token`。登录响应出现 `mfa_required` 或 `mfa_invalid` 时，页面转入二次验证码输入流程。公开实现证明 Dashboard 登录依赖 CSRF 与带 cookie 的交互式会话，并处理 MFA；公开 API 文档没有说明第三方可用 callsign/password 代替 API key 登录。本轮没有找到授权自动化外部网页登录的条款，故不对条款是否禁止作判断，也不建议模拟账号密码会话。

## 当前官方 API v2 合同

OpenAPI 声明的根路径为 `https://api.brandmeister.network/v2/`。下表中的安全要求来自 OpenAPI 每个 operation 的 `security` 字段；本次没有向任何账号设备端点发送认证请求。

| 完整路径 | 方法 | 官方合同与授权 |
|---|---|---|
| `/device/{id}/profile` | GET | 返回 `DeviceProfile`，包含 `staticSubscriptions`、`dynamicSubscriptions`、`timedSubscriptions`、`autoStatic` 等字段。文档说明这是最近连接 Master 已知的设备配置快照，非实时数据，每分钟最多查询一次。OpenAPI 未标记 Bearer 要求。 |
| `/device/{id}/talkgroup` | GET | 返回静态组数组；每项字段包括 `talkgroup`、`slot`，可含 `repeaterid`。OpenAPI 未标记 Bearer 要求，也没有对该路径标注 `/profile` 的缓存限制。 |
| `/device/{id}/talkgroup` | POST | 创建一个静态组；JSON 请求体要求整数 `group` 与 `slot`，需要 Bearer JWT。 |
| `/device/{id}/talkgroup/{slot}/{group}` | DELETE | 从指定设备及时隙移除静态组；需要 Bearer JWT。官方响应说明目标组已删除或本来就不存在时返回 HTTP 200。 |
| `/device/{id}/action/dropDynamicGroups/{slot}` | GET | 清除此设备指定时隙的全部动态订阅；需要 Bearer JWT。该接口是有副作用的 GET，不能当作静态组移除或自动重试操作。 |

OpenAPI 中 `/profile` 的 `DeviceProfile.staticSubscriptions` schema 确实是数组，能够解释旧模块为何读取这个字段；但它是带缓存描述的组合快照。静态组列表专用路径是 `/talkgroup`，所以它更适合写后读回。官方公开 API 文档没有发现“添加一个指定动态组”的设备操作；可核实的动态组动作是查看 profile 快照和清除指定时隙上的全部动态订阅。

## 当前 Dashboard 对时隙的处理

当前官方 Dashboard 的 `DeviceEditPage` 先读取 `/v2/device/{id}` 的设备对象，再按 `status` 选择静态组 slot 面板：`status === 4` 时只开放 `[0]`；其他已载入的状态开放 `[1, 2]`；没有可用设备状态时面板集合是空数组。它将被选 slot 直接放入 POST JSON `{group: talkgroup, slot: selectedSlot}`。界面把 slot 0 标成 DMO，把 slot 1/2 放在 Duplex 组。OpenAPI 只把 slot 定义为整数，没有写枚举范围；当前官方页面实际使用 0、1、2。

因此，隐藏用户可见的 TS 选择器时，应用仍需内部根据 BM 设备 `status` 选 0 或 1/2。状态未知时应禁用静态组添加；默认写入 slot 2 会让 DMO 设备收到不适用的时隙值。WIREX 的 native Homebrew TS2 是本地 DMR 音频/路由配置，不能据此推断 BrandMeister 设备 profile 的 slot。本次没有读取设备状态，也没有对 `460999901` 发请求。

## WIREX 模块检查与本轮修改

原模块位于 [`ui/windows/BmManagement.psm1`](../../ui/windows/BmManagement.psm1)，固定使用 `https://api.brandmeister.network/v2/device/`，为请求添加 `Authorization: Bearer ...`。POST 路径及 `{slot, group}` 请求体、DELETE 路径与当前 OpenAPI 相符。原先读取静态列表时调用 `/profile` 并解析 `staticSubscriptions`，写后也通过该缓存 profile 读回。现在 `Get-BmStaticGroups` 改为调用专用 `/talkgroup`，严格解析顶层 JSON 数组中的 `talkgroup`、`slot` 字段；没有保留旧 profile 对象的兼容解析，因为这是另一个路径的响应格式。新 helper `Get-BmStaticGroupAddContext` 只从 `GET /device/{id}` 的响应提取匹配设备 ID 和整数 `status`，不返回其它设备字段。官方 Dashboard 映射为 `status=4 → slot 0`，`status=0..3 → slot 2`；status 缺失、类型不符或设备 ID 不匹配时，UI 显示未知状态；越界整数显示其当前数值。上述情况都会保留静态列表并禁用 Add。静态列表刷新、API key 变化或设备 ID 变化时读取这份 metadata；写后确认只 GET `/talkgroup`，不重新读取设备 metadata。UI 隐藏时隙控件，行文本显示 `TG {id}`，行对象仍保留 BM 原 slot，Remove 继续使用该 slot。Add 的本地 slot 校验允许 0、1、2；TG 范围、设备 ID 校验、Bearer 写入、写后读回、超时与取消时不自动重发保持原有行为。

[`tools/test-bm-management.ps1`](../../tools/test-bm-management.ps1) 的 fake transport 覆盖专用 GET 路径与数组解析、slot 0 列表/添加、设备状态映射及无效 metadata、POST 后 GET 确认、DELETE 后 GET 确认、HTTP 403 NACK、传输丢失、读回超时、token 不回显、旧 profile 对象拒绝及无效数组字段拒绝。PowerShell 7.6.5 与 Windows PowerShell 5.1 各通过 75 项断言。[`tools/test-bm-management-ui.ps1`](../../tools/test-bm-management-ui.ps1) 在真实 WPF STA 测试窗和 fake transport 下，各版本通过 66 项断言，覆盖设备状态缺失时保留列表并阻止写入、slot 0/2 选择、写后仅列表读回、原 slot 删除，以及 API key/设备 ID 变化时刷新缓存。所有请求均由 fake transport 接管，没有访问 BrandMeister 设备端点或执行 API 写操作。

## 呼号与 DMR ID 链接规则

当前 BM Dashboard 的 Last Heard 模板把 `SourceCall` 生成为 `/#/profile/{呼号}` 链接，并把 `SourceID` 数字另行显示。当前 bundle 定义 profile 路由参数为 `call`；没有找到经官方文档确认的 `#/profile/{数字ID}` 路由。已验证 BM 呼号 profile 的模板为 `https://brandmeister.network/#/profile/{encodeURIComponent(callsign)}`。

RadioID 当前官方 API 文档列出公开只读 `GET /api/dmr/user/`，筛选参数 `id` 与 `id_sel`；直接按 ID 查询可用的 API URL 模板是：

```text
https://database.radioid.net/api/dmr/user/?id={DMR_ID}&id_sel=%3D
```

该 URL 返回 JSON 数据，不是人类可读的 profile 页面。RadioID 的可读 HTML 搜索页能在公共页面上使用，但本轮无法确认一条受官方文档支持、可把 DMR ID 预填入搜索结果页的深链；`/database/view?id=...` 请求触发浏览器检查页，因此不记为已验证的人类可读链接。UI 对未知呼号的来话保留 DMR ID 纯文本；只有获得呼号后才生成 BM profile 链接。RadioID API 文档也要求避免镜像、批量再发布或构建竞争性查询服务；本项目仅生成用户点击后的单条只读查找，不缓存或再发布数据库。

需要人工查号时，可在普通浏览器打开 [RadioID Database Search](https://radioid.net/database/search)，选 DMR 用户搜索项并输入来话 ID 查看结果；这是只读手动步骤，不是已核实的 URL 模板。搜索页面的精确 ID 链接参数目前只核实到 `type=rptr_dmr` 的中继台结果，RadioID 官方页面的公开机器读取又返回 JS 检查页，所以应用对未知呼号仍不生成 RadioID 超链接。
