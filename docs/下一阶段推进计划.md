# WIREX Bridge 下一阶段推进计划

状态：2026-10-25；源码 `5e3343372d9b0427b5c25943a731292e65b1f7ca` 的 clean build、26 项离线测试和便携包 root 审计已完成；新增音量倍率仍待实机听音验收。本文按用户最新决定改为功能覆盖优先。

## 推进原则

先完成软件功能和离线测试，再在功能切片冻结、最终构建完成后集中做 BM、HRI、音量和 RF 实机验收。某一功能的 HIL 尚未执行或未通过，不阻塞其他可独立实现的软件切片。之前用户对 `005c5e8` DIRECT Echo 和 `ab3c5fa` TG91 收听的确认继续作为各自版本的有效历史证据；新音量和后续改动的最终实机项目汇总在[合并联测清单](合并联测清单.md)。UI 继续后置。

## 已确认的结果

- `5e33433` 新增电台回放与手咪上行的独立 PCM 增益设置，默认 `1.0x`/`16x`；本机设置和两个启动参数均通过离线检查。正式 clean build 的 26 项测试全部通过，compiler warning/error 为 0；构建目录 `build/_work/wirex-bridge-5e33433-20261025-064748`，日志 `build/_work/bm-audio-5e33433-build.log`，EXE SHA-256 `C04D62F13173AD11676A3339EEA250B27745BF1056DB36CF53273AAE1DA34B06`。便携包 `build/bm-radio-bridge-5e33433` 已通过 root 审计，实机音量值尚未测试。
- `ab3c5fa` clean build、26 项离线测试和便携包审计已通过。用户已确认 TG91 实机收听正常；这项确认没有附通话次数或时长。
- `005c5e8` 完成一通 DIRECT 个人终端手咪 → BM 中国鹦鹉 460997 → FTX-1 扬声器回声。用户确认回声清晰；会话结构化记录见 [DIRECT 首轮联测验收](DIRECT首轮联测验收.md)。
- 用户已确认 FTX-1 Node Mode 为 DIRECT，并澄清 145.1 MHz RF 音频是在 Bridge 关闭后出现；S 表指示与该音频是否同一时刻尚未确认。Bridge 运行期间是否仍接收 RF 尚无结果。
- 当前 UI 是离线 PySide6 预览与静态状态模型，没有核心 IPC 或设备数据源；用户已决定把 UI 推迟。C4FM RF 节点尚未完成实机验收。

已有单元/loopback 测试验证软件行为，不替代实机验收。`bm_session_test` 覆盖 BM 断链后清应用队列、退避以及重新登录；`bm_bridge_loopback_test` 覆盖接收播放期间断链后清空媒体、拒绝旧 WaveOut 完成通知并允许新会话继续；`bm_voice_pipeline_test` 覆盖有界队列和溢出清理；`pcm_gain_test` 覆盖软件增益的数值、饱和与削顶统计。DIRECT 实机联测只覆盖一次短会话，不能当作长时待机或断网恢复结果。剩余实机项目统一放入合并联测清单，不作为继续实现其他功能的前置条件。

## 优先级与验收

### P0：音量和 PCM 电平

- **当前实现：** 源码 `5e33433` 已允许独立设置 BM→电台回放增益和手咪→BM 发送增益，默认分别为 `1.0x` 和 `16x`，范围均为 `0.25x–16x`。`audio-settings.json` 只存 schema 版本和两项数值；启动器参数 `-RadioPlaybackGain` / `-MicTransmitGain` 覆盖并保存，后续启动恢复。TX 统计在 BM 语音管线接受样本后累计，RX 统计在 WaveOut 成功排队后累计；无运行时热调。clean build、26 项测试和包审计通过。
- **缺口：** 新增的独立设置还没有通过实机听音验证。`005c5e8` 曾有一次清晰回声，但它不覆盖本次两路增益的分别调整、正常说话时的削顶或音量恢复。
- **下一步：** 继续功能实现时维持两路设置边界和统计语义；软件默认值、上下界、覆盖保存和重启恢复用离线测试核验。新音量值的真实听感及削顶观察放入最终合并联测。
- **软件验收：** 默认值和范围正确；边界内参数生效，越界输入被拒绝；覆盖值在下一次启动恢复；合成 PCM 测试确认增益、饱和和削顶统计。不把软件计数当成人耳结果。
- **实机验收：** 见[合并联测清单](合并联测清单.md)，不阻塞其他功能切片。

### P0：断网恢复与退出稳定性

- **当前实现：** `Session` 已实现 transport loss 后清 BM 应用队列、指数退避和重新登录；native `handle_network_loss` 会关闭 PTT gate、要求重新观察松开、取消 TX/RX/HRI 下行、清播放状态并关闭 WaveOut。正常停止在 BM 已 ready 时排队并尝试本机发送 `RPTCL`。离线测试已验证这些软件分支及旧播放完成通知不能污染新一代音频。
- **缺口：** 真实长时间待机、BM 网络中断后恢复、断网时有媒体排队，以及 `Q` 在空闲/通话中的退出尚未实机验证。离线测试已覆盖对应软件分支，这些 HIL 缺口不阻塞其它软件切片。
- **下一步：** 后续软件变更继续运行 `bm_session_test` 与 `bm_bridge_loopback_test`，保持断线清队列、退避重连、旧播放回执隔离和有界退出的断言。将 30 分钟待机、空闲/播放期间断网恢复、`Q` 空闲/通话退出合并到最终实机清单。
- **软件验收：** 离线测试验证 ready 丢失、应用队列清理、恢复登录、新 run 音频代次和退出收尾；日志区分本机 UDP send 返回与远端确认。
- **实机验收：** 见[合并联测清单](合并联测清单.md)，不阻塞其他功能切片。

### P1：LCD 显示当前话者

- **当前实现：** BM 收包和 `CallConfig`/`ReceiveEvent` 能提供远端 Source ID、目标、呼叫类型、TS/CC；日志能记录最近一个已解码头。HRI DLL 的屏幕字段 serializer、消息发送窗口和 FTX-1 LCD 写入链尚未闭合。BM 事件当前没有远端呼号/TA；本机呼号不能代替远端话者。
- **缺口：** 还没有实现或验证 FTX-1 LCD 的呼号/TG/时隙显示、更新和清屏。不能仅凭 HRI PC DigiPanel 的 `Direct:ON/OFF` 文本推断电台显示字段。
- **下一步：** 先以现有 `ReceiveEvent` 建立只在本次 run 有效的当前呼叫状态模型，使用 Source ID、目标、类型、TS/CC，并为 start/update/end/disconnect 写离线测试。单独继续追踪 EXE 导出槽与 HRI serializer 到 UART 的方向和调用者；实际写入协议恢复之前，不构造或发送显示命令。呼号目录查询是数字 ID 之后的可选补充。
- **软件验收：** 离线测试验证有效头更新、同一呼叫资料更新、call end/链路断开清除、旧 run 不覆盖新状态；未映射呼号时显示 Source ID。真实 LCD 观察并入最终清单；PC DigiPanel 和演示状态不能代替电台屏幕。
- **实机验收：** 见[合并联测清单](合并联测清单.md)，待显示字段和串口发送路径有证据后执行。

### P1：会话启停与 DIRECT/RF 路由观察

- **当前实现：** 自动手咪 PTT、BM 上行、BM 私呼返回和 FTX-1 扬声器回放已通过一通 DIRECT 端到端闭环。HRI T3/T0 与下行播放完成顺序有离线测试；`radio_state` 仍保留 `unknown`，T3/T0 记录不作电台 ACK。
- **缺口：** 用户已确认 Node Mode 为 DIRECT，并确认 145.1 MHz RF 音频是在 Bridge 关闭后出现；尚未比较 Bridge 运行待机、下行播放和退出后的 RF 音频/S 表变化。S 表是否与已听到的 RF 音频同时出现仍未知。HRI `NDDIRECT` 尚未映射到三态 Node Mode，不能据该字段判断 Bridge 对 RF 路由的影响。
- **下一步：** 软件功能和离线验证可继续进行。最终联测时，在相同 VFO、频率和 RF 设置下，对照 Bridge 关闭、Bridge 运行待机、单通 BM 下行和 Bridge `Q` 退出后的 RF 声音/S 表；已有 Node Mode 记录为 DIRECT，不重新确认。记录每个阶段的时间和 VFO/频率，不发送模式写入。
- **软件验收：** 状态报告区分 PC COM、HRI PTT 观察、BM 会话与无线电模式；未读到模式字段时保持未知，不从 `NDDIRECT` 推断。对照试验未执行前，不声称 Bridge 运行期间停止 RF 接收。
- **实机验收：** 见[合并联测清单](合并联测清单.md)。

### P2：C4FM RF 节点

- **当前实现：** `listen-91` 是 BM 组呼的被动网络收听预设；`parrot-cn` DIRECT 个人终端走手咪上行和扬声器下行。两者均没有完成 C4FM 空中节点验收，不能将网络下行播放当作 RF 节点转发。
- **缺口：** 当前 Bridge 未实现 C4FM RF→BM 音频入口或 BM→FTX-1 RF 发射路由。也没有证据确定节点模式需要 AP RADIO 还是 AP PC、HRI/USB 的哪条端点提供 RF 接收音频、如何标记呼叫边界，或怎样请求电台发射。`radio_state` 仍为 `unknown`。不能把 DIRECT 已通过的 WaveIn→BM→WaveOut 链当作 RF 节点路径。
- **下一步：** 先按 FTX-1 官方流程确认 AP RADIO/AP PC 的分工和设备设置，再从有证据的 HRI/EXE 源端、发送控制和音频路由恢复节点协议。协议与软件接口明确后，离线构建 RF ingress/egress 状态机、呼叫限时、半双工和尾部处理，并用合成流测试；不发送未恢复的命令。
- **软件验收：** 合成输入验证 RF ingress 与 BM 呼叫头/语音映射；合成下行验证开始、结束、超时、忙碌、异常清理和重复呼叫门控。接口未恢复前不实现 radio write，也不将节点功能标为已实现。
- **实机验收：** RF→BM 和 BM→RF 两条路径都列在[合并联测清单](合并联测清单.md)，AP 模式选项待官方流程分析后填写。

### P2：配置持久化与 UI

- **当前实现：** native 提供 `parrot-cn`、`parrot-global`、`listen-46001`、`listen-91` 和逐项输入的 `manual`；launcher 可发现/选择 COM 与 WaveIn/WaveOut，并保存两项本机音量设置。native 控制台显示运行状态并写脱敏 JSONL。仓库内 PySide6 UI 与 HTML 预览只使用离线快照；没有核心 IPC、设备控制或真实状态适配。
- **缺口：** 固定预设覆盖有限的参数组合；`manual` 每次逐项输入，没有一般化的 Gateway/Master/TG/TS/CC/呼号与设备配置保存。除音量设置外，通用配置恢复尚未实现。运行状态和诊断已有 console/JSONL 来源，但 UI 不读取它们，也不监督 native 生命周期。
- **下一步：** UI 按用户决定推迟。`audio-settings.json` 只保存两项音量数值；Gateway/Master/TG/TS/CC/呼号、Node Mode 和设备端点的一般配置后续单独定义。保留密码在现有 private 文件管理，不把凭据写入一般设置。之后再将 native 的真实 run 快照/有序事件接到 UI，并让 UI 只管理本次创建的一个核心进程。
- **验收：** 离线测试验证 profile 保存/加载、无效值提示、配置与本机凭据分离；UI 只在当前 run 收到有效状态时显示 ready，旧事件/旧 run 不覆盖新状态。停止按钮和窗口关闭走同一有界收尾，并等待本次 native 进程退出；演示数据始终明显标记为模拟。随后由用户确认实际设备发现、启动、状态和退出行为。
- **实机验收：** UI 仍排在核心功能之后；涉及 UI 的设备启动/状态/退出验收并入最终清单。离线实现与测试可以独立推进。

## 官方 Node Mode 与软件控制边界

### FTX-1 模式矩阵

| FTX-1 Node Mode | 官方定义 | 本机已恢复的软件操作 | WIREX Bridge 状态 |
|---|---|---|---|
| AP RADIO | 手册使用 `AP RADIO` 作为 Node Mode 名称，称其为电台侧接入点模式；这个名称本身没有说明是否需要 PC 或互联网软件。 | 用户提供的菜单路径为 `RADIO SETTING → WIRES-X → Node Mode`，可在电台菜单手动选择；尚未找到 EXE 命令切入 AP RADIO。 | 未实现 C4FM RF 音频入口或 RF 发射出口。 |
| AP PC | 手册称 PC 与电台配合，经 C4FM 空中链路工作。 | 用户提供的 `RADIO SETTING → WIRES-X → Node Mode` 菜单可在电台侧手动选择 AP PC。CHM `Transceiver.html` 的 Voice CH 段说明 WIRES-X 经互联网工作，由 PC 控制 Radio 1；FTX-1 可通过 USB Type-C 直接连接 PC。Node-operation 注释也说明不使用 HRI-200 的 PC/电台直连仅支持数字操作。`DirectComPort` 只选择 PC 连接端口，不能作为 AP PC 切换命令。 | PC直连设备的配置/控制路径有官方帮助依据；没有恢复 AP PC 的软件模式写入或 C4FM RF 音频收发协议。 |
| DIRECT | 手册描述 DIRECT 经连接 PC 与电台通信，不经空中发送/接收。手册没有单独解释普通 VFO 接收。 | 用户提供的菜单路径为 `RADIO SETTING → WIRES-X → Node Mode`，可在电台菜单手动选择；用户已确认当前为 DIRECT。尚未找到 EXE 命令切入 DIRECT。 | 本地手咪上行与 BM 下行扬声器播放已验证；Bridge 开/关时普通 VFO FM 接收仍待对照。 |

手册没有在本轮材料中给出可直接复用的 FTX-1 CAT Node Mode 写入命令。固件研究中的 `Node Mode EX010706` 和 `WIRES-X DG-ID EX010704` 是未验证候选，不应写入或发送。HRI `DGKEY_NUM_NDDIRECT` 的 0/非 0 只对应 PC DigiPanel `Direct:OFF/ON` 和 Y 正文候选 `'1'/'2'`；没有三态模式映射证据。

| 动作 | 静态证据 | 能确认的语义 | 尚不能做的事 |
|---|---|---|---|
| WIRES-X 连接/断开远端 Node/Room | CHM `Connect.html` | 官方客户端按 WIRES-X User ID/DTMF ID 发起连接并支持 Disconnect。 | 不是 BM 连接控制，也不设置 FTX-1 Node Mode。 |
| WIRES-X 网络语音转发 | CHM `Status.html` | 已连接时，客户端把 Voice CH 收到的语音转到连接目标。帮助规定本机节点连续发射不超过 3 分钟；目标节点音频的转发会由 HRI-200 硬件计时器在 3 分钟后停止，并说明倒计时显示不与硬件计时器同步。 | 这是 WIRES-X Node/Room relay 流程，不是当前 Bridge 的 BM 呼叫转发；该 3 分钟说明不能替代本机 BM 单通话限制。 |

| HRI frame/数据导出 | 同一 EXE 装载表初始化 `SetDigiTrcvData` 槽 `+0x1c`、`FrameTrxDataToTrcvFrame` 槽 `+0x48`；见屏幕与路由静态报告 | DLL 有内部队列/文本字段解析路径。 | 两个导出到电台 UART 的调用方向、字段和显示写入没有闭合；禁止按候选格式发送。 |

### 可复用的已验证语音路径

可以复用 BM 会话、DMR 编解码、呼叫过滤/Receiver、限长媒体队列、手咪 PTT observation、USB Audio 输入/输出和有界清理代码。`005c5e8` 的一通 DIRECT 自动手咪→BM 460997 私呼回声→FTX-1 WaveOut 已由用户确认清晰；`ab3c5fa` 的 TG91 收听也已由用户确认正常。`5e33433` 为两路 PCM 增益加入离线配置、边界测试和包审计，增益本身尚未实机试听。

这些证据没有验证 C4FM 空中音频如何进入 BM，也没有验证 BM 下行如何令 FTX-1 通过 RF 发射。DMR target/filter 只描述 BM 数据包的匹配条件，不能用来确定 FTX-1 的 RF 频率或 Node Mode；DIRECT WaveOut 只确认本机向所选播放端点输出，尚无 RF 转发证据。
