# S1-E 交接与阶段同步

本文把 S1-E 的范围、状态语义和验收要求保存在 Git 仓库内，供后续审查者直接使用。它总结了更大项目设计中的相关部分，不依赖仓库外的研究文件。完整研究目录不纳入本仓库；其中只有在这里明确写出的脱敏结论可用于 S1-E。

完整产品目标是让 FTX-1 接入 BrandMeister，并支持两种同等重要、分别验收的真实用途：FTX-1 个人终端（DIRECT；本机手咪上行，网络语音由本机扬声器播放，不因网络下行自动做 RF 发射）和本地 C4FM RF 节点（附近 C4FM 电台经 FTX-1 进入网络，网络语音经 FTX-1 发出）。电脑音频只用于诊断，不是第三种产品用途。S1-E 只是首个本地双向语音测试里程碑；后续 BrandMeister codec 转换、网络会话及两种用途各自的射频工作仍在产品范围内。

S1-E native 基础实现已完成并提交，当前进入主会话审阅与操作者 HIL 阶段；真实 UI 监督仍在后续范围内。本文下方区分已完成的离线检查和未执行的硬件验收，不把一类证据当成另一类通过。

## 目标与资源边界

本阶段的 native 基础测试包把电台到电脑监听和用户发起的电脑到电台播放放进同一个 native 进程与同一个 HRI 会话。该进程在一次运行中独占打开 HRI COM 端口，运行总时长最多 120 秒。它还独占所选 USB WaveIn 和电脑 WaveOut。空闲时，WaveIn 采到的电台 USB 音频送到电脑 WaveOut 供操作者监听。

操作者通过控制台按 F/M/C/Q，分别请求固定 WAV、最多 8 秒麦克风内存捕获、取消当前操作或退出；不要求操作者手工输入协议命令文本。固定 WAV 与麦克风音频两条下行路径都按有界的 T3、PCM、T0 顺序处理。实现同一会话内有限的 HRI 握手交换、双向 PCM 音频和停止测试；输出完成或取消清理后，native 恢复电台到电脑的监听。不得由一次业务操作启动第二个 native 子进程、第二个 COM owner，或重开另一个 HRI 会话。不得把音频、协议正文、设备私有 fixture 或凭据写入日志。

已有 UI 协议/状态层保留供后续接入。本阶段不要求真实 UI 子进程监督或应用打包；它们不阻塞 native 基础测试包。后续 UI 监督 native 子进程时不得直接打开设备：创建时先让子进程保持 suspended，监督器把它加入自己拥有的 Job Object，并启用 kill-on-close，再恢复运行。监督器保留进程与 Job 句柄；超时兜底只作用于本次创建的子进程或 Job。UI 通过 stdin 发送命令、从 stdout 收取事件，窗口线程不能等待设备操作或子进程退出。

启动 native 只建立本次会话和监听路径；它本身不代表 HRI 已完成初始化，也不代表电台已连接或处于可发射状态。启动时、空闲时、操作成功时和退出时，radio 状态都显示为 `unknown`，除非之后另有经授权且能读回的设备验证。

## 命令与事件

供后续 UI/自动化接口使用的 stdin 每行是一条 ASCII 命令，首字段是协议版本，接着是当前运行标识、请求标识和命令名。当前操作者使用控制台 F/M/C/Q 入口，不手工输入这些协议行：

```text
1 <run_id> <request_id> send_fixed
1 <run_id> <request_id> capture_mic
1 <run_id> <request_id> cancel_operation
1 <run_id> <request_id> shutdown
```

native 通过 stdout 每行发送一个 JSON 对象，协议版本为 1。事件类型为 `snapshot`、`request_result`、`operation_event`、`operation_result` 和 `session_result`。事件带当前 `run_id`；native 为同一 run 生成递增的 `seq`；与业务操作相关的事件关联发起它的 `request_id`。事件按既定 schema 提供 `status`、`phase`、`hri`、`audio`、`pc_cleanup` 与 `radio_state`。

UI 只把当前 run 且 `seq` 大于最近已处理值的事件应用到画面。UI 将命令 `accepted` 或 `started` 显示为仍在进行，不显示成已完成。只有 native 的最终操作结果才能结束对应的 pending operation。IPC 断开或 native 崩溃后，先前设备状态立即过期，UI 显示核心不可用以及设备收尾未知。

native 在 `shutdown` 时拒绝新操作，完成有限收尾后发出关闭结果并退出。stdin EOF、用户关闭窗口和显式 shutdown 都进入相同的有界清理流程。超过 native 的 120 秒运行上限也必须结束当前工作并清理；UI 不无限等待。如果 UI 监督器最终强制结束子进程，只能显示“核心已强制结束，设备收尾未知”，不能声称电台安全停机。

## 状态与设备结果解释

- `radio_state` 保持 `unknown`，即使 native 报告 T0 写入完成、观察到匹配 T 记录、WaveOut 队列排空或本机句柄关闭成功。
- 本机的 PCM 捕获、排队和播放属于操作结果。它们不能单独证明电台发声、射频停止、PTT 释放或 HRI 已恢复。
- UI 从当前 run 的 native 快照和结果更新状态；不从按钮点击、进程存在、旧报告、`accepted` 或演示数据推导连接状态。
- native 是串口与音频资源的唯一 owner；UI 的 Job 只管理它创建的子进程。任何失败和取消路径都只回收各自拥有的资源。
- 如果已经尝试 T3，取消和错误清理至多尝试一次有界 T0。T3 尚未尝试时取消不得发送 T0。不得猜造其他结束帧。

## 已有证据与限制

截至 S1-E 起点 `87a76b17f245bd1bc183ac245815f7f0aa9f1296`，仓库有 DIRECT 编解码和流解析、HRI 状态机、下行协调器、WinMM 采集/播放、WAV 检查、控制台关闭收尾及其离线测试。S1-D/R69 记录了一次独立固定 WAV 下行人工试听；用户确认能听到清晰报数，播放结束后声音停止且电台界面恢复。原报告同时记录本机串口/音频清理成功，但 `radio_state` 仍为 `unknown`。此前另有独立的 radio-to-PC 原型人工结果。它们是两个不同的单向原型，均不代表 S1-E 同一进程、同一 COM 会话、UI 监督、取消、EOF 或重复运行通过。

R63 的脱敏摘要只支持构造固定 T3/T0 软件候选；R68 的脱敏摘要只支持特定 owner 上有限软件状态请求路径。两者都没有证明 T3/T0 的电台侧 PTT 含义、UART 到达、射频行为或电台恢复。测试和界面不得把匹配 T 记录称为严格关联的设备确认。

固定设备 fixture、固定语音文件和原始报告是操作者本机数据。用户可按本机已授权流程获取、重采或准备所需数据；Git 仓库不保存或推送设备私有 fixture、操作者录音、临时抓包、厂商二进制、凭据或包含原始载荷的报告。若之后需要把人工合成 WAV 作为离线测试 fixture 纳入仓库，先审查该具体文件，再为准确的测试路径添加窄范围例外；不要提交操作者录音或通用 WAV 文件。

## 高风险验收场景

当前先验收 native 基础包，优先使用离线测试或假的传输，不打开真实串口和音频端点。真实 UI 监督和打包另列后续阶段。

1. **单一 owner 与连续监听：** 启动一个会话后确认 COM 只打开一次；空闲的 WaveIn 到 PC WaveOut 路由保持运行。多次播放操作不得创建第二个 native、重开 COM 或留下第二套音频资源。
2. **T3/PCM/T0 及取消边界：** 固定 WAV 和麦克风数据都按预期顺序执行。只有一次 T3 尝试后，任一路径失败或取消最多产生一次 T0 尝试；T3 尝试前取消不产生 T0。PCM 结束或清理后，监听路由重新接收新输入。
3. **麦克风上限与内存：** 验证 8 秒边界、短录音、录音设备启动失败和取消；native 不把 PCM 写到文件、stdout、错误文本或日志。超过上限的数据不排队给 HRI。
4. **最长运行时间与阻塞：** 在会话接近 120 秒上限时开始操作，确认整个 run 仍按一个有限期限退出；串口读写、音频等待、stdin 读取和 T0 清理不会无限阻塞 UI 或 native 主循环。
5. **stdin EOF 与关闭幂等：** 空闲时和活动操作中分别关闭 stdin；再与显式 shutdown、`cancel_operation` 交错触发。每个请求只有一个最终结果，清理只执行一次，过程有界退出。
6. **run/seq/request 隔离：** 保留 UI 协议/状态层测试：注入旧 `run_id`、重复或倒退 `seq`、错配 `request_id` 和迟到事件；UI 不恢复旧快照，不把 `accepted` 当完成，也不让某操作结果结束另一个请求。此项不替代当前 native 控制台验收。
7. **Windows Job 监督（后续 UI 阶段）：** 当前 native 基础包不以此项为门槛。UI 接入时验证 child 在加入 Job 前没有运行；加入后关闭 UI 可结束自己创建的 child。正常 shutdown 等待 native 结果与进程句柄退出；超时只终止持有句柄确认的 child/Job，不触碰无关进程。
8. **失败状态：** COM 占用、音频端点打开失败、短写、T 记录超时、PCM 排队失败、stdout/IPC 断开和强制结束都应保留组件失败与清理结果。所有路径的 `radio_state` 仍为 `unknown`。

本次 S1-E 包目前没有 HIL 结果。用户已授权的本机测试由操作者通过 native 控制台明确开始，并先确认本轮设备状态；启动时不自动按 PTT 或发 RF。下面的高风险场景是待现场 HIL 的验收清单，不表示已经执行。离线状态机、后续 Windows UI 进程监督测试和人工试听是不同证据层，一种结果不能替代另一种。当前 UI、BrandMeister、RF 和完整冷启动也都未验证。

## 可重复构建与离线验证

从本仓库 `app` 根目录运行以下 Windows PowerShell 5.1 命令。脚本通过本机 `vswhere.exe` 查找 VS 2019 Build Tools，不安装工具；native 和测试使用 C++17、`/W4`、`/DNDEBUG`、`/MT`，产物写入 `build\_work`，不删除目录内容。

```powershell
powershell.exe -NoLogo -NoProfile -ExecutionPolicy Bypass -File .\tools\build-radio-session.ps1
```

此命令已对干净源码提交 `732e418bf5b60a99790b00c692601bc95fb1b43c` 实际执行，native 编译无警告，以下 8 项离线测试均以退出码 0 完成：`hri_downlink_session_test`、`hri_radio_protocol_test`、`operation_audio_cleanup_test`、`audio_input_cleanup_test`、`wave_output_open_test`、`session_report_test`、`bounded_pipe_writer_test`、`session_timing_test`。安全失败子进程也验证了缺少 Y 模板、报告父目录不存在、匿名 stdout pipe 满且无人读取、隐藏控制台配无效 COM 等路径；这些测试没有启动会话或打开硬件。验收文档 [`S1-E本地会话验收.md`](S1-E本地会话验收.md) 记录了逐项范围和失败结果。
